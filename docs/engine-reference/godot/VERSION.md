## Knowledge Gap Warning

The LLM's training data likely covers Godot up to ~4.3. Versions 4.4, 4.5,
and 4.6 introduced significant changes that the model does NOT know about.
Always cross-reference this directory before suggesting Godot API calls.

| Glow rework / emissive-to-bloom mapping | ⚠️ Verification Required — **partially characterized 2026-07-13** | `hero.md` (Tower Affinity aura, low-HP vignette), `tower.md` (aura pulse, weapon-lock glow, beam glow, constellation glow border) | Live MCP test on the pinned 4.6.2.stable binary found: (1) an overbright `ColorRect` renders with **no visible bloom halo** in this project's default (LDR, non-HDR) 2D rendering path, even with `glow_intensity=6.0`/`glow_strength=3.0`/`glow_hdr_threshold=0.2`; (2) enabling `Viewport.use_hdr_2d` (required for 2D content to exceed 1.0 and trigger glow meaningfully) **darkens the entire scene globally**, independent of glow or tonemap mode — confirmed by testing `use_hdr_2d=true` alone with glow disabled. **Actionable conclusion**: glow/bloom VFX for this project cannot be a simple "enable WorldEnvironment.glow_enabled" toggle — it requires deliberately opting into `use_hdr_2d` (a whole-viewport exposure change affecting every visual, not just the intended emissive element) and re-tuning overall scene brightness/contrast alongside it. Still needs a full pass with the project's actual planned VFX assets (not a synthetic ColorRect) before texture import presets are locked — this test narrows the risk from "unknown" to "known integration cost," it doesn't close it. |
| `AStar2D` | ✅ Verified — no risk | `pathfinding.md` | Stable API across 4.4–4.6, no changelog-documented behavior changes. Performance separately verified (S4-10 stress test). |
| `sqrt()` | ✅ Verified working | `hero.md`, `tower.md` | Confirmed via actual engine run (S4-12) — `sqrtf()` does NOT exist in Godot 4.6.2 GDScript; `sqrt()` is correct. |
| Global `class_name` resolution via headless `run_project`/MCP tools | ⚠️ Gotcha — not an engine bug, a workflow gap | Project-wide (surfaced by Epic 05: Crafting, Defense Building, Menagerie all affected) | **Discovered 2026-07-18 (Sprint 6, S6-01 live-verification pass).** `.godot/global_script_class_cache.cfg` is only rebuilt by an editor-mode filesystem scan — headless game-runtime execution (MCP `run_project`/`attach_project`) does NOT rebuild it. A project driven only via those tools will silently fail to resolve any `class_name` added since the cache was last built, producing "Could not find type X in the current scope" errors that look like real code defects but aren't. **Fix**: `Godot.exe --headless --editor --path <project> --quit` (runs `update_scripts_classes`, no GUI). See `.claude/docs/context-management.md` → "Godot MCP Session Gotchas" for the full writeup. This masked Epic 05's actual boot status for the entire epic — all 26 stories were marked Complete with tests "created but not executed" and the project had never actually been boot-verified until this discovery. |
| `Resource.duplicate_deep()` | ✅ Verified working (2026-07-19) | ADR-0008 (Tower Placement Gate — 4-component Resource isolation) | Added Godot 4.5, post-LLM-cutoff. ADR-0008 (Accepted 2026-05-19) specifies calling this on 4 nested component Resources (Foundation/Weapon/Focus/Power) at tower-placement commit to isolate mission-instance mutations from inventory data — implementation landed and live-verified via Godot MCP 2026-07-19 (Sprint 7, S7-01): mutating a placed tower's mission-instance component copies (`power.effect_value`, `foundation.damaged`) left the original `TowerBlueprintData` and its own nested components completely untouched, and all 4 component instances confirmed as genuinely distinct objects (`!=` reference comparison). Closes a verification gap that had been open since 2026-05-19. |
| Host-owned killable `Tween` (`create_tween()` stored + `.kill()`) | ✅ Verified working (2026-07-24) | ADR-0032 §3 (Presentation Shell Hosting Pattern), `sanctuary-ui.md` Story 007's own named Edge Case | No post-cutoff API risk — standard 4.x `Tween` lifecycle. Live-verified pattern (not just theoretical): `RoomHost._transition_tween` stores the drawer-slide tween and calls `kill_transition_tween()` at the start of every new `_play_drawer_slide_in()`, closing a real bug found by this session's `/code-review` (an un-stored local-variable tween could otherwise keep stepping a `Control` already `queue_free()`'d by rapid re-triggering). Confirmed via GdUnit4: killing a tween owned by the host (never the room instance) never null-refs, even when the tracked node is mid-teardown. |
| `InputModeTracker` per-room ownership via `get_node_or_null()` lookup (not host-injected) | ✅ Verified working (2026-07-24) | ADR-0011 (UI Dual-Focus Handling), `sanctuary-ui.md` Core Rule 6 | Not an engine-risk item — a project convention correction. `RoomHost` previously constructed and injected a second, unwired `InputModeTracker` into every mounted room; fixed to `get_node_or_null(NodePath(&"InputModeTracker"))` on the room's own child (matching `InventoryScreen.tscn`'s real `$InputModeTracker`). Live-verified via GdUnit4 against both a stub room (with a matching child added to its own `.tscn`) and the real `InventoryScreen.tscn` — the lookup correctly returns `null` for any room with no tracker child rather than erroring. |
| `Control` anchor/size-override warning (`"Nodes with non-equal opposite anchors will have their size overridden after _ready()"`) | ⚠️ Benign, confirmed non-blocking (2026-07-24) | `sanctuary-ui.md` Story 001 (`structural-model_test.gd`) | Surfaces during headless GdUnit4 runs whenever a test sets `.size` directly on a full-rect-anchored `Control` (e.g. asserting Diorama/RoomHost rect math) before Godot's own anchor system re-derives it post-`_ready()`. Confirmed benign in this project's usage: the assertion itself reads the anchor-derived size after settling, not the manually-set value, so the warning does not indicate a real defect — but it's worth knowing this warning is expected/noisy in any test exercising anchor-driven `Control` rects, not a sign the test is broken. |
| `#` comment lines inside a `.tscn`/`.tres` `[node]`/`[resource]` block | 🛑 **Confirmed unsafe — do not use** (2026-08-20) | Epic 15 Story 003 (`adr-0037-visual-presentation-3d-companion-layer.md`) | Live-verified via Godot MCP direct engine load (not guessed): a `# comment` line placed between `[node name="Camera3D" type="Camera3D" ...]` and its `position =`/`rotation_degrees =` property lines caused `position` to silently fail to apply (read back as `Vector3.ZERO` at runtime) while `rotation_degrees` on the same node applied correctly — no error, no warning, just a wrong value. A second attempt with a comment line containing a backtick (`` ` ``) character produced a hard `Parse Error` and failed the entire scene load (`ERROR: Failed loading resource`). Godot's resource text format (`.tscn`/`.tres`) is **not** GDScript and does not reliably support `#` line comments inside node/resource property blocks — behavior ranges from silent property corruption to a full parse failure depending on content, not a simple "comments are ignored" fallback. **Fix applied**: removed all `#` comments from the two affected `[node]` blocks (`the_gap.tscn`, `MissionScene.tscn`); explanatory context moved to the owning script's `_ready()` doc comments instead (a `.gd` file, where `#` comments are always safe). **Rule going forward**: never add `#` comments inside a `.tscn`/`.tres` node or resource block — put explanatory context in the owning script instead. |
| New/edited row in `assets/localization/strings.csv` not reflected in `tr()` output at runtime | ⚠️ Gotcha — not an engine bug, same class of workflow gap as `class_name` cache (see `tests/README.md`'s "Known Gotcha") | Any GDD/UI work touching `strings.csv` | **Discovered 2026-09-16, live-verified via Godot MCP.** `strings.csv`'s compiled `Translation` resource (`strings.en.translation`, gitignored, importer `csv_translation`) is only rebuilt by an editor-mode filesystem scan — a headless game-runtime session (`run_project`/`attach_project`) loads whatever `.translation` was last compiled, not the current `.csv`. Symptom: a newly-added key (e.g. `INVENTORY_TOWER_PREVIEW_HEADER`) renders as the literal key string in-game instead of its translated text, with no error or warning anywhere. **Fix**: same as the `class_name` cache gotcha — `Godot.exe --headless --editor --path <project> --quit` forces the reimport (confirmed via file timestamp: `strings.en.translation` updated to match). Re-verified live afterward: the label read "Preview" correctly. Since the compiled `.translation`/`.import` files are gitignored generated artifacts, there is nothing to commit for the fix itself — each machine (or CI runner) needs its own editor-mode pass after a `strings.csv` edit before headless/MCP verification will show correct text. |
