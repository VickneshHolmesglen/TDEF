## Overview

The Mission HUD is the player's primary heads-up display during a mission. It owns all player-facing feedback that is not part of the world itself: route-preview overlays, blocked-placement indicators, phase announcements, wave progress, hero stats, and deferred-routing notifications. It is the visual and communicative layer that makes the Pathfinding System's silent routing computations legible to the player.

Full design completed 2026-07-14 via `/design-system retrofit`, closing TR-hud-001/002/003's gaps. Scope is mission-context only (SCOUT through DEFEAT/MISSION_COMPLETE) — Sanctuary-context HUD (crafting, menagerie, tech tree, encyclopedia) belongs to the separate, not-yet-started "Sanctuary UI" system. Most of the visual/interaction specification lives in the already-Approved `design/ux/mission-hud.md`; this GDD adds the phase-gated rule layer, the three genuinely new signal-driven elements (route-preview overlay, blocked-cell two-tier emphasis, PC-3 notification), and resolves one real conflict found between two Approved documents (Ready button behavior during PRE_WAVE — see Detailed Rules, Core Rules Group 6).

## Player Fantasy

**The Commander's Certainty**

The Mission HUD is where the player stops guessing. Every placement during Scout Phase redraws the world's intent in front of them — the route bends around a new tower, a blocked cell lights up, the horde's future path resolves into a line the player can read before a single enemy spawns. The fantasy is foresight: to look at the board during Scout Phase and *know* the plan will hold.

**Design hypothesis, not a closed decision — flagged during `/design-review` (2026-07-14):** the route-preview overlay is deliberately withdrawn the instant the wave goes live (Core Rules Rule 6/10). The intent is that this *is* the fantasy's payoff, not a gap in it — vindication as watching the wave break exactly along the path the player already committed to memory, with no overlay left to lean on, rather than watching a static line confirm itself against the monsters walking under it. **This is asserted design theory, not a validated one**, and it sits in real tension with Pillar 1's own explicit anti-pattern (`game-pillars.md`: "difficulty must be opaque — players must be able to diagnose what went wrong" is listed as a violation, i.e. diagnosability is required). For a first-time player who hasn't yet built the pattern-recognition to "just know" the plan held, losing the only confirming instrument at the exact moment chaos begins risks reading as information-loss rather than a trust fall — with no in-mission tool to distinguish "my plan failed" from "the game hid something from me." **This must be validated by playtest, not assumed** — see the new experiential acceptance criterion in this GDD's Acceptance Criteria section. If vertical-slice playtesting shows players report confusion rather than vindication, revisit Rule 10 (candidate mitigations: a brief ghost-trail fade-out instead of instant removal, or a low-opacity "last known route" toggle available on demand during WAVE_ACTIVE).

This foresight is only possible because the HUD never shows the player anything they didn't set in motion themselves. The route it draws is the line their towers carved; the cell it highlights when a placement is rejected (PC-2) is the exact constraint their own spatial reasoning pressed against. The HUD is a conversation between architect and world — the player proposes, the world answers, and the HUD makes that answer legible.

Once the wave is live, the same instrument keeps the player a half-step ahead of the chaos — hero HP, skill cooldowns, tower integrity, a failing boss bar, all read at a glance. But this is a supporting register, not the centerpiece. **Design guardrail**: if a HUD element competes with the collapsing-wave moment for the player's eyes, it has failed its purpose. Legibility exists to serve the plan the player already made — not to become the spectacle itself. The best version of this HUD is confident enough to recede at the exact instant the world tells the story.

## Detailed Rules

### Core Rules

**Group 1 — System Identity & Scope**

1. Mission HUD is a Presentation-layer scene (per ADR-0002's Autoload/Scene-Instanced boundary — not an Autoload), instanced as a static `CanvasLayer` child of `MissionScene.tscn` per ADR-0002's Mission Scene Hierarchy diagram — present in the tree for the entire lifetime of the mission scene, not dynamically added/removed by phase transitions. **"Mounts" and "unmounts" below describe internal state, not scene-tree membership** (resolves a conflict found during `/design-review`, which flagged the original wording as contradicting ADR-0002): "mounts" on `mission_phase_changed(previous_phase == "IDLE", new_phase == "SCOUT")` means reset all local state (Rule 4) and become visible/interactive; "unmounts" on `mission_phase_changed(new_phase in {"MISSION_COMPLETE", "DEFEAT"})` means become hidden/inactive. The node itself is destroyed only when `MissionScene` unloads at the SANCTUARY transition, not before — its own `_ready()`/`_exit_tree()` fire exactly once per mission, at scene load/unload, and that is where its EventBus subscriptions are connected/disconnected (see Rule 6 for the separate, per-wave lifecycle of its Planning Cluster child).
2. This GDD covers mission-context behavior only: SCOUT, PRE_WAVE, WAVE_ACTIVE, INTERMISSION, MISSION_COMPLETE, DEFEAT. Sanctuary-context display (crafting, menagerie, tech tree, gold/material totals outside a mission) is out of scope — see the Dependencies section's scope note on `event-bus.md`'s catalogue.
3. Mission HUD owns no gameplay state. Every displayed value is either a direct read of an EventBus payload or one of the HUD-local derived counters below. It mutates gameplay state only via its three outbound signals (Group 6–8).
4. HUD-local derived state, all reset on mount:
   - `_enemies_alive_display: int` — `+1` on `monster_spawned`, `-1` on `monster_died`/`monster_breached`, `-N` on `monsters_died_batch`, clamped at 0. This is a **display-only** mirror; Wave Manager's own `_enemies_alive` remains the sole authoritative count for wave-clear logic.
   - `_breach_count: int` — `+1` on any `monster_breached`, tier-agnostic, never resets mid-mission.
   - `_active_tower_hp_bars: Dictionary[int, Vector2]` — keyed by `tower_id`, value is `Vector2(current_hp, max_hp)` read directly from the `tower_damaged` payload's own `current_hp`/`max_hp` fields (`tower.md` Rule 22 confirms both fields are present on every `tower_damaged` emission — a single scalar is insufficient to render a fill-ratio bar). Mounted on the first `tower_damaged` for that tower, updated in place on subsequent `tower_damaged` events for the same `tower_id`, cleared entirely on `mission_phase_changed → INTERMISSION` (towers reset to `max_hp` between waves — a stale bar would misrepresent full-HP towers as damaged).
   - `_boss_state: {entity_id, display_name, current_hp, max_hp} or null` — set on `monster_spawned` with BOSS tier **only if `_boss_state == null`**; if a second BOSS-tier `monster_spawned` arrives while `_boss_state != null`, log a warning and discard without overwriting. This should never trigger in practice — `wave-manager.md`'s CI validator (Rule enforcing "no entry at any non-last position may be BOSS-tier," final wave "exactly one BOSS-tier entry as the last entry") guarantees at most one BOSS exists per mission. The guard exists as defense-in-depth, not because concurrent bosses are a supported case. Cleared on `boss_died` **only if the received `entity_id` matches `_boss_state.entity_id`** — a `boss_died` for a non-matching (or already-null) entity_id is treated as stray and discarded, same idempotent spirit as the existing null-state guard in Edge Cases. (Resolves a correctness bug found during `/design-review`: the original unkeyed version would silently swap or wipe the wrong boss's bar if the one-BOSS invariant were ever violated upstream.)
   - `_boss_telegraph_cell: Vector2i` — owned by the outer HUD root (not the Planning Cluster — see Rule 11a's rationale), initialized to sentinel `Vector2i(-1, -1)` on mount. Set from `wave_preview_available.boss_spawn_cell` on receipt (Rule 11a); reset to sentinel on `wave_completed` regardless of cause (Rule 11e — **corrected during `/review-all-gdds` 2026-07-15**, was previously `mission_phase_changed → WAVE_ACTIVE`; see Rule 11e for why). **Added during `/design-review` session #2 (2026-07-15)** — see Group 3b.

**Group 2 — Phase-Gated Existence (the "recede" guardrail, operationalized)**

5. Two clusters exist: the **Planning Cluster** (route-preview overlay, blocked-cell highlight, Tower Build Panel, Ready button, Sell button) and the **Combat Cluster** (Hero HP bar, skill/ultimate cooldowns, breach counter, boss bar, tower HP bars, floating damage numbers).
6. The Planning Cluster is a separate sub-scene (its own `PackedScene`), instantiated as a child of the Mission HUD root on the outer HUD's SCOUT mount (Rule 1) and again on every entry to INTERMISSION; it is `queue_free()`'d — **fully removed from the scene tree**, not dimmed or disabled-in-place — on every entry to WAVE_ACTIVE. **Resolves an implementability gap found during `/design-review`**: re-instantiating fresh from the `PackedScene` each cycle, rather than keeping one persistent instance alive via `remove_child()`/`add_child()`, guarantees `_ready()` re-fires every time — so its EventBus subscriptions (connected in `_ready()`, disconnected in `_exit_tree()`, per the EventBus Core Rule cited in the Interactions table) reconnect correctly every wave. A persistent-instance approach would silently fail to reconnect after the first WAVE_ACTIVE→INTERMISSION cycle, since Godot does not re-fire `_ready()` on `add_child()` of an already-initialized node. **Live-verified 2026-07-14** via MCP `run_script` against the pinned 4.6.2.stable binary: a node re-added via `remove_child()`→`add_child()` held `_ready()`-fire-count at 1 (confirmed no re-fire), while a fresh `instantiate()` of the same `PackedScene` after `queue_free()` correctly fired `_ready()` again on the new instance — this GDD's re-instantiate approach is the only one of the two that reconnects subscriptions on every cycle, not an unverified training-data assumption. During PRE_WAVE the Planning Cluster is present (the same instance carried over from the prior SCOUT/INTERMISSION mount — it is not destroyed or re-instanced at the PRE_WAVE boundary) but only the Ready button remains interactive — everything else in the cluster (build list, cell overlay/cursor, Sell button) is non-interactive, since tower placement is not a valid player action in PRE_WAVE (Wave Manager Rule 7, "Player Actions: None").
7. The Combat Cluster is present in every phase with no layout change and receives no expanded treatment during WAVE_ACTIVE — its role is peripheral awareness, not a second focal point competing with the wave. This is the concrete form of the Player Fantasy's "recede" guardrail: the Planning Cluster disappears entirely once its job is done; the Combat Cluster never grows to fill the space it leaves.
8. Exact visual weight, pixel placement, and animation timing are UX Spec concerns (`design/ux/mission-hud.md`, Approved) — this GDD fixes only the phase-gated *existence* and *interactivity* of each cluster, the contract a programmer needs.

**Group 3 — Route-Preview Overlay (closes a gap PC-1 doesn't cover)**

9. PC-1 (locked, below) covers re-render on `path_invalidated`. It does not cover the very first render. Rule: on `templates_ready` (subscribed independently of Wave Manager's own gate on the same event), HUD calls `PathfindingSystem.get_path(spawn_cell, 0)` once per spawn cell and renders the initial route-preview overlay. This must happen before any tower is placed, so it cannot wait for a `path_invalidated` event (none will have fired yet).
10. On `mission_phase_changed → WAVE_ACTIVE`: route-preview and blocked-cell highlight are removed (Group 2, Rule 6) — this satisfies PC-1's "never re-renders during WAVE_ACTIVE" self-enforcement note by removing the surface entirely, rather than relying only on the triggering event's absence. This is a deliberate Player Fantasy choice, not just an implementation convenience: per the Player Fantasy section's 2026-07-14 clarification, the overlay's withdrawal at this exact moment is when the HUD "lets go" and lets the wave's actual path — read against the plan the player already committed to memory — deliver the vindication payoff.
11. On `mission_phase_changed → INTERMISSION`: the overlay reappears showing the last-known route. It only actually changes if a `path_invalidated` arrives (e.g. PC-3's boss-destroyed-a-tower case, resolved at the INTERMISSION→PRE_WAVE gate per Wave Manager Rule 22).

**Group 3b — Boss-Lane Telegraph (PC-5, closes Tower GDD OQ-11) — added during `/design-review` session #2, 2026-07-15**

This closes a real, previously-blocking gap: `wave-manager.md` Rule 11 emits `wave_preview_available` with a `boss_spawn_cell: Vector2i` field (sentinel `Vector2i(-1,-1)` on non-boss waves) at SCOUT/INTERMISSION entry, and both `tower.md` and `wave-manager.md` explicitly name Mission HUD as the required consumer — this document previously had zero handling for that event at all.

11a. **Subscription ownership**: the outer HUD root (not the Planning Cluster) subscribes to `wave_preview_available` in its own `_ready()` — the same persistent-subscription pattern as Rule 9's `templates_ready` gate. **This is deliberate, not incidental**: `wave_preview_available` fires synchronously on `INTERMISSION`/`SCOUT` entry, in the same call stack as the `mission_phase_changed` event that triggers the Planning Cluster's own re-instantiation (Rule 6) — a Planning-Cluster-owned subscription could not be guaranteed live before that emission, and unlike the one-shot `templates_ready` boot race, this recurs on **every** wave cycle, making a Planning-Cluster-owned subscription an intermittent (not one-time) ordering bug. On receipt, the outer root caches `boss_spawn_cell` into `_boss_telegraph_cell` (Rule 4) and hands it to whichever Planning Cluster instance is currently live, for rendering.

11b. **Sentinel guard**: if `boss_spawn_cell == Vector2i(-1, -1)` (the previewed wave has no boss), `_boss_telegraph_cell` is set to the same sentinel and no marker is rendered or requested — mirrors PC-2's existing `primary_blocking_cell == Vector2i(-1, -1)` handling (Detailed Rules Group 4).

11c. **Rendering**: the telegraph marker's world position is resolved via `Grid.cell_to_world(_boss_telegraph_cell)` — a second read-only direct Autoload call this document makes, alongside Pathfinding's `get_path()` (Rule 9). The marker is a **Planning Cluster-owned visual**: mounted whenever the cluster exists and `_boss_telegraph_cell` is non-sentinel, and requires no separate cleanup of its own — it is destroyed along with the rest of the cluster when `queue_free()`'d at WAVE_ACTIVE entry (Rule 6). **Camera-transform note**: this document has never explicitly specified how PC-1/PC-2's existing grid-cell-to-screen-space conversion works from this `CanvasLayer`-based HUD (Rule 1) — the same mechanism must apply here. This should be live-verified via MCP against the pinned 4.6.2.stable binary (matching this document's own established verification standard — see Rule 6's `_ready()` re-fire test and PC-2's glow/bloom test) before this rule's coordinate-rendering text is considered locked.

11d. **WAVE_ACTIVE spawn-confirmation pulse**: when `_boss_telegraph_cell` is non-sentinel and `monster_spawned(tier="BOSS")` fires during WAVE_ACTIVE, Mission HUD emits a single brief confirming pulse VFX at `Grid.cell_to_world(_boss_telegraph_cell)` (owned by the outer HUD root, since the Planning Cluster housing the persistent marker no longer exists at this point), then clears `_boss_telegraph_cell` to sentinel. **This is a deliberate, narrow exception to Rule 7's "recede" guardrail** — the only Combat-Cluster-adjacent visual this document permits tied to planning information. It is justified because it is not a persistent marker (a single pulse, not an ongoing display) and it delivers the specific in-combat validation moment Tower GDD's OQ-11 exists to serve: confirmation that the boss spawned exactly where the telegraph promised, at the exact instant it becomes true. Without this, the marker's withdrawal at WAVE_ACTIVE (per Rule 6's default) would discard the payoff the whole telegraph was built to provide. If `_boss_telegraph_cell` is already sentinel when a BOSS unexpectedly spawns (should not occur, per Wave Manager's content constraints — see Wave Manager Rule 6's boss-entry requirements), no pulse fires; this is defensive, not an expected path.

11e. **Defensive reset**: `_boss_telegraph_cell` is reset to sentinel on `wave_completed` regardless of whether the Rule 11d pulse fired — belt-and-suspenders against a missed or late `monster_spawned(tier="BOSS")` due to any upstream ordering issue — and on HUD mount (Rule 4). **Corrected during `/review-all-gdds` 2026-07-15 — this rule originally reset on `mission_phase_changed → WAVE_ACTIVE`, which made Rule 11d's pulse structurally impossible to fire.** Wave Manager Rule 6 guarantees the BOSS entry is always the *last* `WaveSpawnEntry` in its wave, preceded by at least one other entry — so the BOSS's `monster_spawned` event is guaranteed to arrive *after* `mission_phase_changed → WAVE_ACTIVE` has already fired for that wave, never in the same frame. Resetting the cell at that same phase-transition event therefore always cleared it before Rule 11d's guard could ever see a non-sentinel value — the confirmation pulse could never fire under any legal content configuration, not merely in a rare race. Binding the reset to `wave_completed` instead preserves the original defensive intent (the cell cannot leak into the *next* wave's preview cycle — `wave_completed` always fires before the next wave's `wave_preview_available`, per Wave Manager's own phase lifecycle) while allowing Rule 11d's pulse its full window during WAVE_ACTIVE to actually fire.

**Group 3c — Wave Composition Preview Display (closes tower.md Rule 8's composition-bucketing mandate) — added 2026-07-15d, `/review-all-gdds` 4th pass**

This closes the other half of `wave_preview_available` that Group 3b never covered: `tower.md` Rule 8 and `wave-manager.md` Rule 11 both require Mission HUD to display the upcoming wave's monster count and tier mix during SCOUT (full) and INTERMISSION (partial) — this document previously had no handling for the `composition` field at all, only for `boss_spawn_cell`.

11f. **Resolution — INTERMISSION (tier-bucketed)**: on receiving `wave_preview_available` during an INTERMISSION mount, for each `WaveCompositionEntry` in `composition`, the outer HUD root (same subscription ownership as Rule 11a, for the same reasons) resolves that entry's tier via `GameDataRegistry.get_monster(entry.monster_id).tier` and accumulates `entry.count` into one of three running totals: `STANDARD`, `ELITE`, `BOSS`. This is a synchronous, read-only static-data lookup — no EventBus round trip, no caching required (recomputed fresh on every `wave_preview_available`).

11g. **Resolution — SCOUT (full composition)** *(corrected 2026-07-15d — `/review-all-gdds` 5th pass found the original draft of this rule silently collapsed SCOUT to the same tier-only view as INTERMISSION, contradicting `tower.md` Rule 8's explicit text: SCOUT's Wave 1 preview must deliver "monster types, counts, tier" as "complete information for the initial commitment," distinct from Intermission's deliberately partial tier-only read)*: on receiving `wave_preview_available` during the SCOUT mount, the outer HUD root instead renders the full per-entry breakdown directly from `composition` — each `WaveCompositionEntry`'s `monster_id` alongside its `count`, with no tier aggregation. No new payload field is needed — `composition` already carries everything this requires; only the display path differs by phase. **Revised 2026-08-16 (player-requested, "UI Changes.PNG"):** each entry now resolves `monster_id` to that monster's real sprite icon (`MonsterInstance.MONSTER_TEXTURES`, the same art already rendered on the live monster) instead of `display_name` text, per-entry, with a text fallback to `display_name` for any `monster_id` with no authored art yet (matches this project's established icon-with-text-fallback convention, e.g. `mission_hud.gd`'s materials chip row). The underlying data/lifecycle (Rules 11h/11i) are unaffected — only the per-entry visual changed from text to icon.

11h. **Display**: SCOUT renders the full per-monster-type list (Rule 11g); INTERMISSION renders the tier-bucketed totals (Rule 11f, e.g. "12 monsters: 10 STANDARD, 2 ELITE"). This asymmetry is the intended implementation of `tower.md` Rule 8's Scout-informed / Intermission-meta-read contrast — it is not a display inconsistency to reconcile. Exact typography/layout for both is a UX Spec concern (`design/ux/mission-hud.md`).

11i. **Lifecycle**: both displays are owned by the Planning Cluster instance (same `queue_free()`-on-WAVE_ACTIVE lifecycle as the route-preview overlay, Rule 6) — re-populated fresh from the next `wave_preview_available` on every SCOUT/INTERMISSION mount, never carried over or diffed against the previous wave's data. Which rule (11f or 11g) runs is determined by which phase the Planning Cluster was just (re)instantiated into — not by inspecting event payload content.

**Group 4 — Blocked Placement (PC-2)**

12. No additional phase guard is needed — `tower_placement_blocked` can only fire during SCOUT/INTERMISSION because placement itself is locked outside those phases (Tower/Pathfinding enforce this upstream). Presentation is exactly as specified in PC-2 below.

**Group 5 — Deferred Routing Notification (PC-3)**

13. On `tower_destroyed` received while `phase == WAVE_ACTIVE`: display a non-modal banner, "Path update queued for next intermission," top-center, auto-dismiss after 3 seconds.
14. At most one such banner exists at a time. A second `tower_destroyed` while one is already showing re-triggers/resets the 3-second timer rather than stacking a second banner.
15. The banner is purely informational — it gates no player action — and is force-dismissed on `mission_phase_changed → INTERMISSION` if still visible at that point.

**Group 6 — Ready Button (`player_ready` emitter)**

16. Ready exists and is interactable during SCOUT, PRE_WAVE, and INTERMISSION. It does not exist during WAVE_ACTIVE, MISSION_COMPLETE, or DEFEAT. **This resolves a conflict found during authoring**: `design/ux/mission-hud.md` originally stated Ready is disabled during PRE_WAVE, but `wave-manager.md` (Approved) Rule 10 + EC-8 explicitly requires it to remain active — pressing it during PRE_WAVE cancels the countdown and transitions immediately to WAVE_ACTIVE ("a commander who has resolved the debrief... presses Ready and commits early"), and Wave Manager's GDD states in EC-8 that "Mission HUD should NOT disable the Ready button during PRE_WAVE." Wave Manager is the authoritative phase-gate owner; this GDD follows its rule. **The UX spec was corrected 2026-07-14** (Layout Hierarchy row 7, States & Variants "PRE_WAVE", Interaction Map, Transitions, and Acceptance Criteria — see its Open Question #9) to match.
17. Press → emit `player_ready` (no payload) immediately, synchronously, every time the button exists and is interactable. No additional HUD-side phase guard — Wave Manager Rules 9/10/12 are the sole authority (defense in depth, same pattern as Sell below).
18. During PRE_WAVE, the button's presented meaning changes from "confirm and advance" to "skip the countdown" — same event, different player-facing intent. Exact label/state treatment is a UX Spec concern.

**Group 7 — Ultimate Button (`hero_ultimate_activated` emitter)**

19. Exists in all phases. Interactable only when `cooldown_remaining == 0` for `skill_slot == Hero.ULTIMATE_SLOT_INDEX` (reserved index 4, per `hero_skill_cooldown_updated`). While on cooldown, the button consumes no input and emits nothing.
20. Press (while interactable) → emit `hero_ultimate_activated` (no payload) immediately, synchronously. HUD does not predict or locally reset the cooldown display — it waits for the next `hero_skill_cooldown_updated` tick, same as every other cooldown-driven display element.

**Group 8 — Sell Button (`tower_sell_requested` emitter)**

21. Exists only when `phase in {SCOUT, INTERMISSION}` **and** a tower is currently selected/inspected in the Tower Info Panel. Does not exist in PRE_WAVE, WAVE_ACTIVE, MISSION_COMPLETE, or DEFEAT.
22. Press → emit `tower_sell_requested(tower_id: int)` for the currently-inspected tower, immediately, synchronously. HUD clears the Info Panel selection optimistically but does not remove the tower visually or adjust any counter until Tower System's confirming event (`tower_removed`) arrives.

**Group 9 — Cross-Cutting Emitter Rules**

23. All three outbound signals fire synchronously on the Godot `pressed` signal — never deferred. These originate from UI input, not a physics callback or scene-tree mutation, so EventBus Core Rule 3's synchronous default applies; deferring would add a needless frame of input latency to a player-initiated action.
24. All three buttons (plus any other focusable Mission HUD control) follow ADR-0011's `InputModeTracker` pattern: one `InputModeTracker` instance owned by the Mission HUD scene (not shared with any other screen), explicit `focus_neighbor_*` wiring across the full tab order, and a focus ring shown only when `has_focus() AND tracker.is_focus_ring_visible()`, independent of mouse hover.

**Group 10 — Retry Button, DEFEAT-only (added 2026-07-17, closes `mission-select.md`'s flagged gap)**

25. Exists only in the `DEFEAT` state, on the outcome/Defeat screen this doc's DEFEAT row already establishes takes over from the fading Planning/Combat clusters. Does not exist in any other phase. A second, separate "Abandon to Sanctuary" action is also present on this screen (per `mission-select.md`'s States table) but is out of scope here — Mission HUD owns its presence, not its behavior, since it has no EventBus or Autoload effect this GDD tracks.
26. Press → calls `MissionSelect.retry_current_mission()` directly (a **direct Autoload call, not an EventBus event** — `mission-select.md` Rule 10 documents this as a deliberate, narrow exception to EventBus-only communication, the same class of exception Grid's own Rule 8/9 already use). This is the only place in Mission HUD's entire event-emitter surface that calls another system's Autoload directly rather than emitting through EventBus — flagged here explicitly since it breaks this doc's otherwise-universal "HUD only ever emits, never calls" pattern (Groups 1–8 above).
27. Following the call, Mission HUD does not locally predict or handle the resulting `mission_launched` re-emission — it reacts to it exactly like an initial mission launch (Rule 4's counter reset), since `retry_current_mission()`'s contract (per `mission-select.md` Rule 10/EC-6) guarantees a fresh `mission_launched` firing before any other mission-context event.

### Confirmed Signal Contracts (from dependency GDDs)

The following contracts are fixed and must be honoured by the Mission HUD implementation. They are documented here to prevent the dependency GDDs from referencing an undesigned system.

**PC-1 — `path_invalidated(affected_cells: Array[Vector2i])` (Pathfinding GDD Rule 10, OQ-5):**
- Subscribe via EventBus.
- On receipt: call `PathfindingSystem.get_path(spawn_cell, 0)` to obtain the updated route. `affected_cells` is the union of changed-walkability cells (the tower footprint) — it is NOT the route. Do not render `affected_cells` directly as a route line.
- Re-render the route-preview overlay with the new path.
- Do NOT re-render during WAVE_ACTIVE — placement is locked during active waves and `path_invalidated` cannot fire in that phase, so this constraint is self-enforcing. If `path_invalidated` is somehow received during WAVE_ACTIVE, discard without re-rendering.

**PC-2 — `tower_placement_blocked(blocked_cells: Array[Vector2i], primary_blocking_cell: Vector2i)` (Pathfinding GDD Rule 10):**
- Subscribe via EventBus.
- On receipt: highlight `blocked_cells` to indicate the rejected footprint.
- If `primary_blocking_cell != Vector2i(-1, -1)`: highlight `primary_blocking_cell` distinctively (e.g., brighter color, pulsing outline) to anchor player attention to the specific load-bearing constraint cell.
- If `primary_blocking_cell == Vector2i(-1, -1)`: highlight all `blocked_cells` uniformly — the footprint as a whole is the constraint, no single cell is individually load-bearing.

**PC-3 — `tower_destroyed(tower_id, grid_position, footprint)` during WAVE_ACTIVE (Pathfinding GDD EC-11):**
- Subscribe via EventBus.
- On receipt during WAVE_ACTIVE: display a player-visible communication indicating "Path update queued for next intermission."
- The specific presentation (banner, pop-over, audio cue) is to be determined during full HUD design.

**PC-5 — `wave_preview_available(next_wave_number, composition, boss_spawn_cell: Vector2i)` (Wave Manager GDD Rule 11) — added during `/design-review` session #2, 2026-07-15, closes Tower GDD OQ-11:**
- Subscribe via EventBus, from the outer HUD root (Rule 11a).
- On receipt: cache `boss_spawn_cell` as `_boss_telegraph_cell` (Rule 4).
- If `_boss_telegraph_cell == Vector2i(-1, -1)` (sentinel): no marker rendered (Rule 11b).
- Otherwise: hand the cached cell to the currently-live Planning Cluster instance, which resolves it via `Grid.cell_to_world()` and renders the boss-lane telegraph marker (Rule 11c). Marker is destroyed with the rest of the Planning Cluster at WAVE_ACTIVE entry (Rule 6).
- On `monster_spawned(tier="BOSS")` during WAVE_ACTIVE, if `_boss_telegraph_cell` is non-sentinel: fire a single confirming pulse at that cell (owned by the outer root, since the Planning Cluster no longer exists), then clear to sentinel (Rule 11d).
- `_boss_telegraph_cell` is unconditionally reset to sentinel on `wave_completed` (Rule 11e — corrected 2026-07-15; NOT on `mission_phase_changed → WAVE_ACTIVE`, which would clear it before the boss's `monster_spawned` could ever arrive).

**PC-4 — Wave progress and phase transitions:**
- Resolved by `design/ux/mission-hud.md` (Approved) — subscribe to `mission_phase_changed`, `wave_started`, `phase_timer_tick`, `wave_countdown_warning` and display phase indicator, wave counter, and phase timer/enemy count per that spec's Zone A component inventory and States & Variants table. See this GDD's States and Transitions table above for the phase-cluster existence rules that govern when each element mounts.
- The UX spec originally stated the Ready button is disabled during PRE_WAVE, which contradicted `wave-manager.md`'s Rule 10/EC-8 (Ready must remain active in PRE_WAVE to allow skipping the countdown). This GDD's Core Rules Group 6 (Rule 16) resolved the conflict in Wave Manager's favor; the UX spec was corrected 2026-07-14 to match.

## Formulas

None. Mission HUD is a pure display/counter layer — every value it shows is either a direct EventBus payload read or a simple increment/decrement local counter (Core Rules Group 1, Rule 4). Timing values (e.g. the PC-3 banner's 3-second auto-dismiss) are configurable constants, captured in Tuning Knobs below, not formulas. No system in this GDD computes a derived value from multiple inputs.

## Edge Cases

- **If a stray `boss_died` (Monster System's EC-5b force-removal cleanup) arrives after the legitimate `boss_died` already cleared `_boss_state`**: no-op, idempotent — the boss-state handler must guard against acting on an already-null state, not inherit Wave Manager's own stray-guard (which only protects Wave Manager's internal state).
- **If `boss_hp_changed` arrives while `_boss_state == null`** (subscription-order nondeterminism at spawn, or after `boss_died` already cleared it): discard silently. EventBus's ghost-event silence (EC-3) covers the bus, not HUD's own internal struct access — this GDD states the null-guard explicitly.
- **If `tower_destroyed` fires for a tower still tracked in `_active_tower_hp_bars`**: `_active_tower_hp_bars.erase(tower_id)` immediately, not just at the next INTERMISSION's wholesale clear — otherwise a destroyed tower's HP bar lingers for an entity no longer on the grid.
- **If `tower_damaged` arrives for a `tower_id` not currently tracked as alive** (out-of-order delivery after `tower_destroyed`/`tower_removed` already fired for that id): discard. HUD only accepts `tower_damaged` for towers between their `tower_placed` and their `tower_destroyed`/`tower_removed`.
- **If `tower_destroyed` (PC-3) and `wave_completed`'s INTERMISSION transition fire in the same frame, with `tower_destroyed` processed after the phase has already flipped**: the PC-3 banner does not show. This is accepted as a deliberate, order-dependent non-issue — the underlying stale-route condition still resolves via Wave Manager's own rebuild-pending gate, so the banner's absence causes no functional harm, only a missed notification.
- **If `path_invalidated` arrives while `phase == PRE_WAVE`**: treat identically to INTERMISSION (re-render the route-preview on receipt) — the Planning Cluster overlay is still visible (non-interactive but visible per Core Rules Rule 6) during PRE_WAVE, and only WAVE_ACTIVE excludes re-rendering.
- **If `path_invalidated` were somehow received during the exact frame WAVE_ACTIVE begins**: PC-1's "discard if received during WAVE_ACTIVE" clause (not filler — the actual last line of defense) applies. This should be structurally prevented by Wave Manager's rebuild-pending gate (`wave-manager.md` Rule 22), which guarantees any pending rebuild completes before PRE_WAVE→WAVE_ACTIVE proceeds; PC-1's discard clause exists only as a safety net if that gate has a bug.
- **If `templates_ready` fires before Mission HUD's `_ready()` has finished connecting subscriptions** (a boot-order race at mission start): Rule 9's one-shot initial route render would be permanently missed, with no fallback trigger since it explicitly cannot wait for a `path_invalidated` event. **Resolution**: HUD's mount handler additionally polls `PathfindingSystem` for already-ready templates as a fallback, in case the ghost-event window was missed.
- **If a new mission starts before a prior Mission HUD instance's teardown has fully completed**: not possible by design — each mission launch loads a fresh `MissionScene.tscn` instance (per Rule 1's ADR-0002 alignment), and Mission HUD, as its static child, is destroyed and recreated along with it. There is no scenario where two Mission HUD instances for different missions coexist; this guarantee is stated explicitly rather than left implied by "mounts/unmounts" language.
- **If combat events continue arriving in the same frame a terminal `mission_phase_changed` (MISSION_COMPLETE/DEFEAT) fires, before the scene's `_exit_tree()` actually runs** (`queue_free()` is end-of-frame, not instant): latch a `_terminal` flag on receipt of the terminal phase change and short-circuit all further Combat/Planning Cluster mutation handlers for the rest of that instance's life — the same `_phase_locked`-first pattern Wave Manager itself uses.
- **If the player mashes Ready across the SCOUT→PRE_WAVE→WAVE_ACTIVE boundary faster than the scene removes the button**: a stray `player_ready` may fire in the one-frame lag before `queue_free()`. Resolved as a non-issue by design — Wave Manager already silently ignores `player_ready` received during WAVE_ACTIVE (defense in depth, Rule 17's stated philosophy); no additional HUD-side guard needed.
- **If the player double-presses Ultimate before the confirming `hero_skill_cooldown_updated` returns**: Mission HUD applies no debounce by design (Rule 20) — Hero System is solely responsible for rejecting or ignoring a second activation received before its own cooldown state updates. This cross-system assumption is stated explicitly so it's auditable, not silently assumed.
- **If the player rapidly sells two different towers before the first `tower_removed` confirms**: both `tower_sell_requested` calls (different `tower_id`s) can be in flight simultaneously — this is fine structurally, but Tower System's confirmation handling must key strictly off `tower_id`, never a single global "sell in progress" flag.
- **If `tower_sell_requested` is rejected or its confirming `tower_removed` never arrives** (e.g. a bug elsewhere): accepted as a rare, acceptable-loss edge case at MVP — no timeout/error-recovery path is defined. The Info Panel stays optimistically cleared; a future revision may add re-sync-from-next-Tower-event recovery if this proves to be a real problem in practice.
- **If any event fires after Mission HUD has unmounted**: resolved cleanly by EC-2 (disconnect-first in `_exit_tree()`) and EC-3 (ghost events silent) — named explicitly here because Mission HUD subscribes to more distinct event types than almost any other system, and DEFEAT in particular can fire mid-WAVE_ACTIVE with monsters/towers still actively emitting combat events, making this the single highest-traffic teardown window in the game.
- **If `constellation_activated`/`constellation_deactivated` fire before Constellation's owning GDD is Approved and locked**: Mission HUD implements zero handling logic for these until that payload contract is locked — treat as ghost events (EC-3) until this GDD is amended. **Corrected 2026-08-31**: `mastery_progress_updated` no longer belongs in this bullet — Tower Mastery has been Approved since 2026-07-17, and `skill_tree_point_earned`/`skill_tree_overflow_point_earned` both have a real, specified treatment now (Group 11).
- **If `hero_skill_cooldown_updated` fires for `skill_slot` 0–3** (the out-of-scope skill buttons 1–4): received (ghost-consumed) and discarded — Ultimate reads only `skill_slot == Hero.ULTIMATE_SLOT_INDEX`, all other slot updates are not routed anywhere.
- **If `wave_stalled`'s "X enemies remaining" warning is still showing when the wave force-clears** (`wave_completed` arrives): force-dismissed, matching the PC-3 banner's treatment (Rule 15) for consistency — not left to linger into INTERMISSION.
- **If `wave_preview_available` fires twice for the same upcoming wave** (e.g. a resend, or any future Wave Manager retry path): the second event's `boss_spawn_cell` fully overwrites `_boss_telegraph_cell` — no stacking of two markers, matching this document's other last-write-wins patterns (e.g. `_boss_state`'s single-slot tracking). *(Added during `/design-review` session #2, 2026-07-15.)*
- **If `wave_preview_available` fires before a freshly-instantiated Planning Cluster (Rule 6) has completed its own `_ready()`** (the per-cycle race Rule 11a is designed to prevent): not possible by construction — the subscription lives on the outer HUD root (which always exists), not the Planning Cluster, so no ordering dependency on the cluster's instantiation exists. `_boss_telegraph_cell` is cached at the root regardless of the cluster's readiness and handed to it once live. *(Added during `/design-review` session #2, 2026-07-15.)*
- **If `monster_spawned(tier="BOSS")` fires during WAVE_ACTIVE while `_boss_telegraph_cell` is already sentinel** (should not occur per Wave Manager's content constraints, but treated defensively): no confirmation pulse fires — Rule 11d's pulse requires a non-sentinel cached cell. *(Added during `/design-review` session #2, 2026-07-15.)*

## Visual/Audio Requirements

Most of this HUD's visual specification is already Approved in `design/ux/mission-hud.md` (layout zones, component styling, transitions, color-redundancy rules, reduced-motion variants). This section covers only the three elements that spec doesn't define — all new to this GDD authoring pass, art-directed against `design/art/art-bible.md`'s established vocabulary.

**PC-1 — Route-preview overlay**: dashed/painted-stroke line in Scout Blue (Art Bible 2.2), ~40–55% opacity, static (no glow, no pulse), redrawn instantly on route change. Small directional chevrons at turn points as an optional non-color reinforcement. Reads as "the commander's own plan sketched on the board" — fits the Player Fantasy's authorship register — and stays in the peripheral/no-first-read tier so it never competes with towers, monsters, or the Hero for attention.

**PC-2 — Blocked-cell two-tier emphasis**: no glow/bloom is used (this session's live engine test confirmed Godot 4.6 glow requires `Viewport.use_hdr_2d`, which darkens the entire scene, not just the emphasized element — ruled out for a placement-feedback overlay). Two tiers distinguished by four independent non-color channels, all in reduced-saturation Threat Crimson (Art Bible 4.2's "blocked/can't-do-that" hue):

| Channel | Tier 1 — all blocked cells | Tier 2 — `primary_blocking_cell` |
|---|---|---|
| Hatch pattern | wide-spaced diagonal | tight/dense diagonal |
| Outline | thin (1–2px), static | thick (3–4px), static |
| Fill opacity | ~30–40% | ~50–60% |
| Icon glyph | none | small chamfered-square lock/X glyph, centered |
| Motion | none | subtle outline-only scale breathe (2–4%, slow, well under the 3-flashes/sec accessibility threshold) |

This satisfies the project's shape-before-color accessibility discipline independent of the glow constraint — colorblind players can distinguish "primary" from "also blocked" via pattern density, outline weight, and the icon alone.

**PC-3 — "Path update queued" notification**: reuses `design/ux/mission-hud.md`'s existing Pattern 10 (Phase Transition Banner — already used for wave-cleared/wave-incoming) rather than introducing new HUD chrome. Re-skinned with a warm-amber UI accent (Art Bible 4.4's "controlled, known space" signal — the deliberate opposite register from the breach-event screen-edge flash's alarm crimson) and a map-mark icon. Regular type weight (Bold is reserved for headers/damage numbers). Snappy-in, eased-out motion, no bounce (bounce is reserved for MISSION_COMPLETE). Signals "state changed, being handled, no action needed from you" — distinct in tone from the breach flash's "this is a crisis."

**PC-5 — Boss-lane telegraph marker** *(added during `/design-review` session #2, 2026-07-15 — closes Tower GDD OQ-11)*: this is neither Scout Blue (PC-1's "the plan I authored" register) nor Threat Crimson (PC-2's "rejected placement" register) — it communicates a different fact entirely: an authored truth about the future, threat-flavored but not a rejection. **Art Director decision (2026-07-15): Boss Purple.** HSL 275°, 45%, 40% / `#6B3B8F` — a desaturated, static-marker variant of the Art Bible's reserved boss-escalation hue (Art Bible 4.1/4.2, "Purple = elite enemy status and boss escalation only," now formally registered as **Boss Purple**, full-saturation anchor HSL 275°, 60%, 45% / `#7E2EB8`). This is the correct hue for three reasons: (1) it borrows purple's existing "threat-above-red" register rather than inventing a fifth threat-adjacent hue, and purple in this game means one thing only — boss — which is exactly what this marker is telegraphing; (2) it is trivially distinct from Scout Blue, Threat Crimson, and the breach-event alarm crimson at a glance and in grayscale-adjacent testing (hue, not just value, separates it from every sibling color in this HUD); (3) it resolves the Art Bible's own standing constraint (Section 4's WAVE_ACTIVE HUD addendum) that any HUD element rhyming with the WAVE_ACTIVE ambient purple push must fire as the *primary* signal, not an echo — PC-5's marker necessarily renders at SCOUT/INTERMISSION, well ahead of the WAVE_ACTIVE approach window, so that ordering requirement is satisfied by construction. The marker uses the desaturated variant (not the full-saturation ambient-push value) specifically so the static planning-phase signal reads as *information*, not yet as *dread* — full-saturation Boss Purple stays reserved for the WAVE_ACTIVE ambient push, preserving an escalation relationship between the two (same hue, rising intensity) rather than diluting purple's scarcity by using its most intense form twice. Must apply the same shape-before-color discipline as PC-2 (hatch/outline/opacity/glyph/motion, not a bare color highlight) — this is required, not optional, given a boss-spawn cell can visually coincide with an existing PC-1 route-preview line originating from the same spawn cell, and the two must remain distinguishable in grayscale and under line-occlusion. First appearance should be accompanied by a brief contextual callout (legend/tooltip or reuse of PC-3's banner pattern) since this is a genuinely new information category with no onboarding precedent elsewhere in this HUD. The Rule 11d spawn-confirmation pulse should use a motion cadence distinct from PC-2's Tier-2 breathing (2–4%, slow) so the two "something is happening here" motions aren't perceptually identical at a glance. **Asset/animation spec — RESOLVED 2026-07-15 in `design/ux/mission-hud.md`** (that spec's "PC-5 — Boss-Lane Telegraph Marker: Asset & Animation Spec," under Layout Specification): the marker reuses the `☠` skull glyph already established as this HUD's Boss nameplate icon, on a centered opaque badge that stays legible under an occluding PC-1 route line; a diamond-outline + cross-hatch cell treatment (both distinct in shape from PC-2's square-outline/single-diagonal-hatch, on top of the hue difference); a one-shot 0.5s scale-punch + expanding-ring confirmation pulse (with a non-scaling reduced-motion variant) that is categorically distinct from PC-2's continuous slow breathing; and a once-per-mission Pattern 10 first-appearance callout banner with a Boss Purple accent. This GDD fixes only existence, lifecycle, and the shape-before-color/distinctiveness requirements above (same scope boundary as Rule 8 elsewhere in this document) — the concrete presentation values now live in the UX spec.

**Audio**: not yet specified — no `design/audio/` bible exists at time of writing (same gap noted in `game-concept.md`). Deferred until audio direction is authored.

## Acceptance Criteria

Validated by `qa-lead` before finalizing. Organized by Core Rules group, then the three locked signal contracts, then load-bearing edge cases. Six items flagged by that review as not independently testable as GDD-level runtime criteria are omitted here and noted at the end instead.

### Group 1 — System Identity & Scope

- [ ] **GIVEN** `MissionScene.tscn` has just entered the tree (Mission HUD present as its static child per ADR-0002, but not yet internally "mounted"), **WHEN** EventBus emits `mission_phase_changed(previous_phase="IDLE", new_phase="SCOUT")`, **THEN** all local counters reset (Rule 4) and the HUD becomes visible/interactive within the same frame — no scene-tree add occurs, since the node was already present.
- [ ] **GIVEN** Mission HUD is internally mounted (visible/interactive), **WHEN** EventBus emits `mission_phase_changed(new_phase="MISSION_COMPLETE")` or `new_phase="DEFEAT"`, **THEN** the HUD becomes hidden/inactive by end of frame; the node itself persists until `MissionScene` unloads at the SANCTUARY transition.
- [ ] **GIVEN** `_enemies_alive_display` reset to 0 at mount, **WHEN** `monster_spawned` fires 3 times, then `monster_died` fires once, then `monsters_died_batch(count=2)` fires, **THEN** the displayed count reads 0 (never negative, clamped).
- [ ] **GIVEN** `_breach_count = 0` at mount, **WHEN** `monster_breached` fires once in Wave 1 and once in Wave 2 (crossing an INTERMISSION boundary), **THEN** displayed breach count = 2 — the counter does not reset at INTERMISSION.
- [ ] **GIVEN** a `tower_damaged` event was received for `tower_id=7` (bar mounted), **WHEN** `mission_phase_changed → INTERMISSION` fires, **THEN** the HP bar for `tower_id=7` is cleared.
- [ ] **GIVEN** `tower_damaged(tower_id=7, current_hp=180.0, max_hp=330.0, damage_dealt=50.0)` fires, **THEN** `_active_tower_hp_bars[7] == Vector2(180.0, 330.0)` and the rendered bar's fill ratio is computable as `current_hp / max_hp` without any additional lookup.
- [ ] **GIVEN** no boss is present, **WHEN** `monster_spawned(tier="BOSS", entity_id=42)` fires, **THEN** a boss bar mounts showing that entity's HP; **WHEN** `boss_died(entity_id=42)` subsequently fires, **THEN** the boss bar is removed.
- [ ] **GIVEN** `_boss_state` is set for `entity_id=42`, **WHEN** a second `monster_spawned(tier="BOSS", entity_id=99)` fires before 42 dies, **THEN** `_boss_state` is unchanged (still tracking 42, not overwritten to 99) and a warning is logged. **WHEN** `boss_died(entity_id=99)` (the never-tracked boss) subsequently fires, **THEN** it is discarded as stray and the bar for 42 is unaffected.

### Group 2 — Phase-Gated Existence

- [ ] **GIVEN** `phase=SCOUT`, **THEN** all Planning Cluster nodes (route-preview overlay, blocked-cell highlight layer, Tower Build Panel, Ready button, Sell button when a tower is selected) are present in the tree and interactive.
- [ ] **GIVEN** phase transitions to `WAVE_ACTIVE`, **THEN** the Planning Cluster root node is absent from the tree (a node lookup returns null) — not merely hidden or disabled.
- [ ] **GIVEN** `phase=PRE_WAVE`, **THEN** Ready is present and interactive AND Tower Build Panel, the cell overlay/cursor, and Sell are present but reject input.
- [ ] **GIVEN** phase cycles SCOUT → PRE_WAVE → WAVE_ACTIVE → INTERMISSION, **THEN** Combat Cluster nodes (Hero HP bar, cooldown UI, breach counter, tower-HP-bar container, boss-bar container) remain present with unchanged transform/anchor/size across all four phases (excluding boss bar's own contextual mount/dismount).

### Group 3 — Route-Preview Overlay

- [ ] **GIVEN** `phase=SCOUT` and no tower has been placed yet, **WHEN** `templates_ready` fires, **THEN** Mission HUD calls `PathfindingSystem.get_path(spawn_cell, 0)` once per spawn cell and the overlay renders those paths — verified non-empty before any `tower_placed` has occurred.
- [ ] **GIVEN** WAVE_ACTIVE ends with no `path_invalidated` received during that wave, **WHEN** phase transitions to INTERMISSION, **THEN** the overlay reappears showing the identical path last rendered pre-WAVE_ACTIVE.
- [ ] **GIVEN** `phase=INTERMISSION`, **WHEN** `path_invalidated(affected_cells)` fires, **THEN** the overlay updates to a new path via `get_path()`; given no such event fires, the overlay does not change.

*(Rule 10's removal-on-WAVE_ACTIVE is the same observable behavior as Group 2's second criterion — not duplicated.)*

- [ ] **GIVEN** the mission completes two full wave cycles (SCOUT → PRE_WAVE → WAVE_ACTIVE → INTERMISSION → PRE_WAVE → WAVE_ACTIVE → INTERMISSION), **WHEN** `path_invalidated` fires during the *second* INTERMISSION, **THEN** the overlay still updates via `get_path()` — proving the Planning Cluster instance re-instantiated at the second INTERMISSION entry has live, correctly-reconnected EventBus subscriptions, not just the first. *(Regression test for Rule 6's re-instantiate-over-reuse justification — a persistent-instance bug would only surface on this second cycle, per this GDD's own stated rationale.)*

### Load-Bearing Edge Cases

- [ ] **GIVEN** `_boss_state` is already null, **WHEN** a second `boss_died` fires, **THEN** no error occurs and no state change happens.

- [ ] **GIVEN** `phase=PRE_WAVE`, **WHEN** `path_invalidated` fires, **THEN** the overlay re-renders identically to the INTERMISSION case.
- [ ] **GIVEN** `DEFEAT` (or `MISSION_COMPLETE`) has just fired, **WHEN** a combat event (e.g. `monster_died`) arrives in the same frame before teardown completes, **THEN** it produces no display mutation.

- [ ] **GIVEN** `hero_skill_cooldown_updated(skill_slot=2)` fires, **THEN** no HUD element updates (only `slot==4` drives Ultimate).
