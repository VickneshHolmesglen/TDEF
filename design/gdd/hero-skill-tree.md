## Overview

The Hero Skill Tree is a per-adventure spend-progression layer inserted between Tower Mastery and the existing Hero Skill Build System. It replaces Tower Mastery's automatic "100% mastery = skill unlocked" behavior with a spendable point economy: crossing a mastery threshold grants the hero one skill tree point in the mastered tower's archetype, and mastery accrual continuing past that threshold (already an existing, deliberate Tower Mastery behavior) grants further points at each subsequent threshold multiple — rather than instantly handing over a specific skill. The player then spends banked points, at Sanctuary between missions, to advance one of four fixed, linear, archetype-keyed node chains (physical / ranged / elemental / support), each a `[Minor_1, Choice_1, Choice_2, Choice_3]` sequence unlocked strictly in order. **Revised 2026-09-01 for the PoE-scale skill roster**: each `Choice` node presents a set of 2–3 mutually-exclusive options drawn from that archetype's `opener`/`core`/`capstone` tier of `hero-skill-build.md`'s 32-skill catalogue (8 per archetype) — purchasing one permanently locks out its siblings for that playthrough (Rule 8), so which skill a character ends up with is a real, irreversible choice, not a fixed catalogue lookup. The real decision this system introduces is therefore two-layered: **which of the player's four archetype pools to advance first** (points are earned unevenly, based on what was actually mastered), and **which option to take at each Choice node** — together these determine the hero's build identity, PoE-style. A node that represents a real skill still fires the existing `skill_unlocked(skill_id, source_tower_id)` event, unchanged in shape, the moment it's purchased — so the Hero Skill Build System, Mission HUD, and Encyclopedia all keep consuming it exactly as they do today. Only the trigger moves: from "automatic, the instant mastery crosses 100%" to "player spend, gated by an earned point and an already-unlocked predecessor node."

## Player Fantasy

> You used to earn a skill just by standing your ground. Fight beside the same kind of tower long enough, and the game simply handed you what it had to teach — automatic, unasked-for, whatever came next on the list.
>
> Now standing your ground earns you something smaller and more honest: a point. Proof that you mastered this archetype a little further, with no promise yet of what it buys. You carry that proof home to the sanctuary, and there — quiet, unhurried, no wave bearing down on you — you decide what your mastery was actually for.
>
> Within a single archetype, the path is fixed — you don't get to skip ahead, and the stat node nobody brags about comes before the skill everybody wants. That's deliberate: mastery is not a moment, it's a sequence, and you don't get the ending without the middle. But the real decision was never *which* node comes next inside one path — it's *which path you walk first*. You mastered four kinds of towers this run, maybe unevenly, and you're standing in front of four separate proofs of that: banked points in physical, none yet in support, a couple in elemental. Do you round out the archetype you've nearly finished, or start climbing the one you've been neglecting? That's the question the sanctuary actually asks you — not "what order will this one path take," but "which of everything you've earned matters to you most, right now."
>
> And the moment the points get spent is not an afterthought squeezed between missions — it is genuinely rationed. Each time you return, the sanctuary lets you make exactly one purchase, no matter how much you've banked everywhere else. You stood in front of everything four different kinds of mastery had earned you, and the sanctuary made you choose — not because it's stingy, but because a choice that costs nothing isn't a choice. Every path you don't advance this visit is a path that genuinely waits, not a path you'll get to in the same breath. The fight three missions from now is easier for the archetype you picked today, and only that one.

> That's the honest shape of the choice: not which mastery matters *instead of* the rest forever — you'll walk every path eventually, nothing here is lost for good — but which one earns its keep *soonest*, one visit, one decision, at a time. And a tower mastered so thoroughly its lesson is already spent doesn't stop teaching you either — its overflow becomes the wildcard that saves whichever path you're the furthest behind on, right up until there's nothing left to save. Master everything, eventually, and the lessons simply stop coming — not because they were taken back, but because there's nothing left for a tower to teach you. That, too, is proof of something: not a reward left waiting, just the quiet of a student who has nothing left to learn.

## Detailed Design

### Core Rules

#### Group 1: Points & Archetype Pools

1. The hero has **4 skill tree point pools**, one per archetype (`physical` / `ranged` / `elemental` / `support`), each a non-negative integer starting at 0. Points are **per-adventure** (reset to 0 on a new game), matching the existing per-adventure persistence of skills themselves (`hero.md` Rule 11).

2. **Tower Mastery's accrual is unchanged.** `mastery_time` accumulation per `build_signature` (`tower-mastery.md` Rules 1, 3, 10, 12), the proximity radius, and the catalogue's per-entry `mastery_threshold_seconds` all continue exactly as documented there — **including Rule 14, "`mastery_time` accrual does not stop once a skill unlocks... to support a future next-tier skill on the same build signature without needing a data migration."** This GDD is that future consumer: Rule 3 below is built directly on top of Rule 14's existing extensibility hook, not a new accrual mechanism.

3. **Revises `tower-mastery.md` Rule 13.** Each catalogue entry's `mastery_threshold_seconds` now triggers **repeating** grants, not a single one-time unlock: every time `mastery_time[build_signature]` crosses another whole multiple of that entry's `mastery_threshold_seconds`, Tower Mastery emits `skill_tree_point_earned(archetype, source_tower_id)` (new event, same "representative live tower_id" rule as the old `skill_unlocked`) — instead of ever emitting `skill_unlocked` directly. Tower Mastery's own `_unlocked_skills` dictionary (`tower-mastery.md`'s persisted state) is **retired by this revision**, replaced by a new persisted counter `points_granted_count[build_signature]: int`, starting at 0. **Ownership, corrected 2026-08-31 (closes a double-grant bug found by `/review-all-gdds`)**: Tower Mastery's own responsibility ends at emitting the event — it never touches `skill_tree_points` itself. The Skill Tree System is the sole owner of `skill_tree_points[archetype]` and is the only code that mutates it, in its own `skill_tree_point_earned` handler (Rule 3a below). This also removes the need for Tower Mastery to call into the Skill Tree System at all (see Rule 3b/Group 5 — Overflow) — Formula 3 in `tower-mastery.md` is now purely about `mastery_time`/`points_granted_count`, with zero cross-system reads. See Formula 1 for the exact multiple-crossing arithmetic and Dependencies for the save-migration note.

3a. **Point crediting (Skill Tree System's own event handler).** On receiving `skill_tree_point_earned(archetype, source_tower_id)`: if `archetype`'s 4-node chain still has at least one locked node, `skill_tree_points[archetype] += 1`. If `archetype`'s chain is already fully unlocked, the point is never discarded — see Rule 3b (Overflow) instead.

3b. **Overflow points (closes the "Tower Mastery goes dead late-game" problem found by `/review-all-gdds`).** A single, archetype-agnostic persisted counter `overflow_points: int` (starting at 0, per-adventure like the 4 pools) exists alongside the 4 archetype pools. Whenever `skill_tree_point_earned` names an archetype whose chain is already fully unlocked (Rule 3a's "else" branch) AND at least one other archetype still has a locked node, the point converts to overflow instead of being lost: `overflow_points += 1`, and a new event `skill_tree_overflow_point_earned(source_tower_id)` fires (its own Mission HUD notification -- archetype-neutral, since overflow has no single archetype identity). Overflow points are a wildcard: they may be spent on any node in any archetype whose chain still has a locked node, substituting for that archetype's own pool when it's empty (Formula 2). They are never converted back into archetype-specific points, and archetype-specific points are never converted into overflow except by this rule. This keeps Tower Mastery's positioning wager meaningful for almost the entire playthrough -- mastering any tower, in any archetype, produces something spendable somewhere, right up until literally everything is spent (Rule 3c covers that terminal case).

3c. **Terminal completion state (revised 2026-08-31, third pass -- replaces a same-day gold-conversion design that a further re-review found had 3 real problems: it contradicted `resource-economy.md`'s own "no other gold income path" claim; it stacked unboundedly across simultaneously-mastered towers per `tower-mastery.md`'s own established parallel-accrual rule, a real farming exploit; and it broke both this system's and Tower Mastery's Player Fantasy, which promise a permanent reward, while gold resets every mission).** Once ALL 16 nodes across all 4 archetypes are unlocked (every chain fully spent, no locked node anywhere in the tree), Rule 3b's own condition ("at least one other archetype still has a locked node") is false for every subsequent crossing by construction, so no further code path is even needed: a `skill_tree_point_earned` crossing in this state simply matches neither Rule 3a's nor Rule 3b's branch and produces no effect. Tower Mastery keeps emitting the event forever regardless (`tower-mastery.md` Rule 14) and `mastery_time`/`points_granted_count` keep advancing on that document's side, but nothing further happens here. This is an intentional, quiet terminal state -- the tree is complete, and mastering additional towers no longer produces new currency of any kind, the same way any other "you've finished this" end-state elsewhere in the game goes quiet without inventing a replacement reward.

4. Because points are archetype-keyed rather than `build_signature`-keyed, two different build signatures sharing an archetype (e.g., two distinct physical-archetype tower builds) both feed the same `physical` pool — mastering either (or both), and continuing to master either past its first threshold, both contribute points toward the same physical-branch chain. This is also what makes cross-archetype allocation (Player Fantasy) a real, uneven decision in practice: a player who spent the mission camped beside physical towers banks physical points faster than support points, regardless of how many nodes each chain has.

5. Points are **not** consumed the instant they're earned. They accumulate in the pool until the player spends them (Group 3). There is no cap on banked points — this is a deliberate divergence from `resource-economy.md`'s comparable capped-currency convention, acceptable here because unlike a material stack, an uncapped skill tree point pool cannot be spent on anything but this system's own bounded 4-node chains, so there is no external economy for it to distort.

#### Group 2: Node Chain Structure

6. **Revised 2026-09-01 (PoE-scale content pass — `hero-skill-build.md`'s catalogue grew from 8 to 32 skills, 8 per archetype; this revision fits that growth into the same tree shape rather than growing the tree itself).** Each archetype has a **fixed, linear, ordered chain of exactly 4 nodes**: `[Minor_1, Choice_1, Choice_2, Choice_3]` — 16 nodes total across all 4 archetypes, unchanged in count from the pre-expansion design. `Minor_1` is unchanged: a small stat/passive bonus, content-authoring deferred (Group 4). `Choice_1`, `Choice_2`, and `Choice_3` are **new node types, replacing `Skill_1`/`Skill_2`** — each is a mutually-exclusive pick among that archetype's skills at one of `hero-skill-build.md` Rule 3's three `tier` values: `Choice_1` offers the 2 `opener`-tier skills, `Choice_2` offers the 3 `core`-tier skills, `Choice_3` offers the 3 `capstone`-tier skills (2+3+3 = 8 skills per archetype, matching the catalogue exactly). Purchasing a Choice node requires selecting exactly one of its offered skills (Rule 9, revised) — the others are never purchasable at that node for the remainder of the playthrough (Rule 8, revised).

7. A node is purchasable if and only if: (a) its archetype's point pool (or overflow, Rule 3b) has ≥1 point, AND (b) it is the first not-yet-unlocked node in its chain — i.e. its predecessor (if any) is already unlocked. `Minor_1` has no predecessor and is always purchasable once ≥1 point exists in that archetype. For a Choice node specifically, "purchasable" means the player may open it and select among its still-available options (see Rule 9) — not that a specific option is pre-selected.

8. Purchasing a node deducts exactly 1 point from that archetype's pool (or overflow) and marks the node permanently unlocked for the remainder of the playthrough. Unlocking is **never** reversible or re-purchasable — same one-way permanence precedent as skills themselves. **Revised 2026-09-01**: for a Choice node, this permanence extends to the *unchosen* options — the instant one option is selected, every other option at that same node becomes `LOCKED_OUT` (a new terminal state, distinct from `locked` — see Edge Cases), never purchasable this playthrough, whether or not the player ever banks another point in that archetype. This is the real, PoE-flavored trade-off the expanded catalogue is built around: choosing `phys_shatter_slam` at `Choice_2` means `phys_whirling_assault` and `phys_juggernaut_charge` are gone for this character, not merely deferred.

9. **Revised 2026-09-01.** When the purchased node is a Choice node (`Choice_1`/`Choice_2`/`Choice_3`), the player selects exactly one of its still-available skill options at the moment of purchase; the Skill Tree System emits `skill_unlocked(skill_id, source_tower_id)` for the chosen skill only, using `source_tower_id = -1` (sentinel — see Edge Cases for why a live tower reference is never available at spend time), and marks every other option at that node `LOCKED_OUT` in the same atomic operation (Rule 8). This is the **only** place `skill_unlocked` now fires; Tower Mastery no longer emits it directly (Rule 3).

10. **When the purchased node is `Minor_1`**, no `skill_unlocked` event fires — there is no choice, `Minor_1` is a single fixed effect, unchanged from the pre-expansion design. The Skill Tree System instead emits `skill_tree_node_unlocked(archetype, node_index)` (for Mission HUD / Encyclopedia / UI consumers that want minor-node visibility — see Dependencies) and applies the node's stat/passive effect directly (effect format deferred, Group 4, same precedent as `effect_data`).

#### Group 3: Spend Location

11. Skill tree points may be spent **only at Sanctuary, between missions** — never during `SCOUT`, `WAVE_ACTIVE`, `INTERMISSION`, `OUTCOME`, or `DEFEAT` (corrected 2026-08-31 — the original wording omitted `OUTCOME`/`DEFEAT`, which `hero-skill-build.md`'s LOCKED state and `sanctuary-ui.md`'s entry condition both already treat as pre-Sanctuary). This matches the existing lock precedent already shared by Hero Skill Build slot changes (Rule 4), Tower component slots (`tower.md` Rule 3), and Hero class designation (`hero.md` Rule 18): every player-configurable loadout system in the game commits at Sanctuary, not mid-fight.

12. Points earned mid-mission are simply added to the relevant pool immediately (Rule 3a) and sit banked, spendable the next time the player is at Sanctuary. There is no cap on banked, unspent points.

13. **Per-visit spend cap (new 2026-08-31, closes the "no real decision" Player Fantasy defect found by `/review-all-gdds`; persistence corrected 2026-08-31, second pass, closing a free-purchase exploit the same review found).** At most **1 node purchase total** — drawing from any archetype's own pool or from overflow — is permitted per Sanctuary visit, regardless of how many points are banked across however many pools. `visit_spend_count: int` **is persisted** (via Save & Persistence, alongside this system's other state), and resets to `0` exactly when `mission_launched` fires — marking the current Sanctuary visit as ended — **not** on generic `SANCTUARY` (re)entry and **not** on app relaunch. A new adventure (Rule 8) also resets it to 0. Increments by 1 on each successful purchase (Formula 2). Once `visit_spend_count == 1`, no further purchase is permitted until the *next* `mission_launched` has fired and the player has returned to Sanctuary again. **This is what makes "which of everything you've earned matters to you most, right now" (Player Fantasy) a real, binding choice**: with 4+ pools and possibly overflow all holding purchasable points on a given visit, the player must pick exactly one — the other purchasable nodes wait, genuinely, until a mission is actually played and the player returns. **Corrected 2026-08-31, second pass — closes a real exploit**: the original design made `visit_spend_count` ephemeral, resetting on any Sanctuary entry including app launch. This meant purchase → Save & Quit → relaunch → cap reset → purchase again defeated the cap entirely, for free, using a completely ordinary menu action (`save-persistence.md` Rule 4's manual Save & Quit) — not an edge case a player would need to hunt for. Persisting the counter and gating its reset on `mission_launched` specifically (a real mission must actually be played) closes this: a save/quit/reload while still at Sanctuary preserves the current visit's already-spent allowance exactly.

#### Group 4: Deferred Content

14. *(renumbered 2026-08-31, third pass — was duplicated as "13" alongside Group 3's per-visit spend cap rule; purely a numbering collision, no cross-reference depended on the old number)* `Minor_1`/`Minor_2` node effect data (the actual stat/passive bonus each grants) is deferred content-authoring work, same precedent as `hero-skill-build.md`'s `effect_data` field and Tower's component effect fields — this GDD specifies the tree's *structure and economy*, not the minor nodes' numeric tuning. 8 total minor nodes (2 per archetype × 4 archetypes) need this content before Alpha completion. **Unlike `effect_data`'s deferral, this one is load-bearing**: Rule 7 gates `Skill_1` behind `Minor_1` already being purchased, so undesigned Minor node content blocks meaningful playtesting of the entire chain, not just that node's own flavor. Minor node content must be authored *before* implementation begins, not left as a trailing content pass after the system ships.

### States and Transitions

No new hero states. The tree's own per-node state is a simple one-way `locked → unlocked` transition (Rule 8) — the same one-way boolean-latch shape the rest of this project's permanent-unlock systems already use (e.g. Hero Skill Build's own learned-skill flags).

## Formulas

### Formula 1: Threshold Crossing → Point Grant (revises `tower-mastery.md` Formula 3)

**Revised 2026-08-31 — split into a grant side (Tower Mastery, unconditional) and a credit side (this system, Rule 3a/3b).** The prior draft had Tower Mastery call `all_nodes_unlocked()` on this system before granting, both duplicating the pool-increment write (a real double-grant bug) and creating an undeclared direct cross-system call. Tower Mastery's side is now simple and self-contained:

```
# Tower Mastery's side (tower-mastery.md Formula 3, mirrored here for this document's own completeness)
points_earnable = floor(mastery_time[build_signature] / mastery_threshold_seconds)
new_points = points_earnable - points_granted_count[build_signature]

if new_points > 0:
    archetype = archetype_of(build_signature)
    for i in range(new_points):
        emit skill_tree_point_earned(archetype, source_tower_id)   # unconditional — no chain-state check here
    points_granted_count[build_signature] = points_earnable
```

```
# This system's side — the actual state mutation (Rule 3a/3b/3c)
on skill_tree_point_earned(archetype, source_tower_id):
    if all_nodes_unlocked(chain[archetype]) and any_archetype_has_locked_node():
        overflow_points += 1
        emit skill_tree_overflow_point_earned(source_tower_id)
    elif not all_nodes_unlocked(chain[archetype]):
        skill_tree_points[archetype] += 1
    # else: this archetype's chain is full AND every other archetype's chain is also full —
    # Rule 3c's terminal state, revised 2026-08-31 third pass. No branch matches; no effect.
```

`archetype_of(build_signature)` derives the archetype the same way `tower-mastery.md` Rule 4/`tower.md` Rule 5 already do — from the build signature's Foundation component — **not** a lookup against a `catalogue[build_signature].archetype` field, since `tower-mastery.md` Rule 7's catalogue schema (`skill_id`, `source_build_signature`, `mastery_threshold_seconds`, `output`) has no such field.

`source_tower_id` uses the same "lowest live `tower_id` sharing this signature" rule as `tower-mastery.md` Rule 12/13. `new_points` is almost always 0 or 1 per frame given per-physics-frame evaluation and realistic accrual rates, but the loop form is correct even if multiple thresholds are crossed in one evaluation (e.g. after a long period without an update) — each crossing fires its own `skill_tree_point_earned` event rather than silently batching them into a single grant, so Mission HUD's live notification (Dependencies) shows one event per point, matching how a player would expect to see it.

**A build signature's income is genuinely uncapped, permanently.** `mastery_time[build_signature]` and `points_granted_count[build_signature]` keep advancing forever (Rule 2/`tower-mastery.md` Rule 14), and Tower Mastery keeps emitting `skill_tree_point_earned` forever, with no chain-completion check on its side at all. What changes once an archetype's chain fills is only what this system's own handler does with each further point (Rule 3b — it becomes overflow instead of a same-archetype credit), so nothing is ever wasted and Mission HUD's notification is never "purposeless" the way an early draft's unconditional-stop would have made it. This is also what makes a 4-point archetype chain actually completable from as few as 1 mastered build signature per archetype, and what keeps standing beside a well-mastered tower meaningful for the entire playthrough, not just until the local chain is spent.

**Threshold sourcing for uncatalogued build signatures (resolves an ambiguity `/review-all-gdds` found between `tower-mastery.md` Rules 7 and 12).** `mastery_threshold_seconds` is read from `tower-mastery.md`'s catalogue entry for `build_signature` **if one exists**; if no catalogue entry exists for that signature, the global `MASTERY_UNLOCK_THRESHOLD` tuning knob applies instead — matching Rule 7's original phrasing ("defaults to the global... knob unless the catalogue entry overrides it"). This was always the intended reading (it's what makes `hero-skill-tree.md` Rule 4's promise — "any physical-archetype build feeds the same pool" — actually true for the other 999 possible physical loadouts, not just the 2 the catalogue happens to name) but was never made explicit until this pass. Point income is therefore **never** gated to only the 8 pre-authored loadouts.

### Formula 2: Node Purchase

**Revised 2026-08-31** (per-visit spend cap, Rule 13, and overflow-point substitution, Rule 3b); **revised again 2026-09-01** (Choice nodes replace fixed Skill nodes, per Rule 6's PoE-scale content pass — a purchase now includes a player-selected option and a lock-out step for the rest of that node's siblings):

```
if visit_spend_count >= 1:
    purchase_allowed = false   # this visit's single purchase is already spent
elif all_nodes_unlocked(chain[archetype]):
    purchase_allowed = false   # no locked node exists in this chain — nothing to buy, not an error
else:
    node = chain[archetype][next_locked_index]
    has_own_point = skill_tree_points[archetype] >= 1
    has_overflow = overflow_points >= 1
    purchase_allowed = (has_own_point OR has_overflow) AND (node == first_locked_node_in_chain)

if purchase_allowed and player_confirms:
    if skill_tree_points[archetype] >= 1:
        skill_tree_points[archetype] -= 1
    else:
        overflow_points -= 1   # substituting a wildcard overflow point for this archetype's own
    visit_spend_count += 1
    node.unlocked = true
    if node.type == "Minor":
        apply node.effect_data
        emit skill_tree_node_unlocked(archetype, node.index)
    else:  # "Choice" — player_selected_skill_id must be one of node.tier_skill_ids
        for skill_id in node.tier_skill_ids:
            if skill_id == player_selected_skill_id:
                node.chosen_skill_id = skill_id
                emit skill_unlocked(skill_id, source_tower_id = -1)
            else:
                node.locked_out_skill_ids.append(skill_id)   # permanent, this playthrough — Rule 8
```

`player_selected_skill_id` is required input for any Choice-node purchase — Formula 2 does not run at all without it (there is no "purchase the node, decide later" intermediate state; the UI must present all `node.tier_skill_ids` and require a selection before confirming, per Sanctuary UI's own spend-screen requirements). `node.tier_skill_ids` is populated once, at content-authoring time, from `hero-skill-build.md` Rule 3's `tier` field grouped by archetype (`Choice_1` = that archetype's 2 `opener` skills, `Choice_2` = its 3 `core` skills, `Choice_3` = its 3 `capstone` skills) — never computed live, since the catalogue itself never changes at runtime.

The `visit_spend_count` check runs first, before any pool math, so the per-visit cap is enforced uniformly regardless of which chain or pool the player is looking at. The `all_nodes_unlocked` guard is evaluated **before** indexing into the chain — `next_locked_index` is only well-defined when at least one node is still locked, and this check must run first so a fully-cleared chain never attempts an out-of-bounds lookup. This is a real correctness requirement, not just a UX nicety: since Formula 1's income is uncapped (a build signature keeps producing `skill_tree_point_earned` past chain completion — see Rule 3b), every archetype legitimately reaches "fully unlocked, more points still incoming (as overflow)" as normal end-state play, not an edge case that's rare enough to ignore. An archetype's own pool is always drawn from before overflow, so overflow is only ever spent when the archetype itself has nothing banked.

### Worked Example

Player masters a physical-archetype tower build (`found_bulwark_t2`, `mastery_threshold_seconds = 60`) mid-mission; `mastery_time` crosses 60s for the first time. `points_earnable = floor(60/60) = 1`, `points_granted_count` was 0, so `new_points = 1`.
→ Tower Mastery emits `skill_tree_point_earned("physical", source_tower_id=7)` once, unconditionally. `points_granted_count[build_signature]` set to 1. This system's handler receives it: `physical`'s chain has locked nodes, so `skill_tree_points["physical"]` goes from 0 → 1.
→ Mission continues; no chain node is purchasable mid-mission (Rule 11) regardless of pool balance.
→ At the next Sanctuary visit, `visit_spend_count = 0`. The physical chain shows `Minor_1` as the only purchasable node (Rule 7 — `Choice_1`/`Choice_2`/`Choice_3` are all still locked behind it). Player spends the 1 banked point on `Minor_1`: `skill_tree_points["physical"]` goes to 0, `visit_spend_count` becomes 1, `Minor_1.unlocked = true`, `skill_tree_node_unlocked("physical", 0)` fires. Even though the player also has banked points in another archetype this same visit, Rule 13's per-visit cap means no further purchase is possible until the next Sanctuary entry.
→ The player keeps mastering the *same* `found_bulwark_t2` build signature across two more missions. `mastery_time` reaches 190s total. `points_earnable = floor(190/60) = 3`, `points_granted_count` was 1, so `new_points = 2` — Tower Mastery fires two more `skill_tree_point_earned("physical", ...)` events (one per crossing), `points_granted_count` set to 3. This system credits both to `skill_tree_points["physical"]`, which reaches 2 banked.
→ Player returns to Sanctuary (`visit_spend_count` resets to 0) with `skill_tree_points["physical"] = 2` but can still only spend 1 this visit. They open `Choice_1` (the physical archetype's opener tier: `phys_cleave` vs. `phys_rending_throw`) and select `phys_cleave`. Formula 2 fires `skill_unlocked("phys_cleave", -1)`, marks `Choice_1.chosen_skill_id = "phys_cleave"`, and appends `"phys_rending_throw"` to `Choice_1.locked_out_skill_ids` — permanently, this playthrough, per Rule 8. `visit_spend_count` becomes 1; the remaining banked physical point, along with `Choice_2`/`Choice_3` still locked, waits for the visit after next.
→ Two Sanctuary visits later, the player opens `Choice_2` (the core tier: `phys_shatter_slam` vs. `phys_whirling_assault` vs. `phys_juggernaut_charge`) and selects `phys_whirling_assault` — a channeled spin that better complements the piercing-throw playstyle they've been leaning into. `phys_shatter_slam` and `phys_juggernaut_charge` are both permanently locked out for this character; a different playthrough choosing differently at `Choice_1` and `Choice_2` would end up with a mechanically distinct physical-archetype hero, the real build-differentiation payoff this catalogue expansion was built for.
→ Much later, having long since fully unlocked the physical chain (`Choice_3` resolved too), the player masters another physical-archetype signature. Tower Mastery emits `skill_tree_point_earned("physical", ...)` as always; this system's handler finds `all_nodes_unlocked("physical")` true, so the point becomes overflow instead: `overflow_points += 1`, `skill_tree_overflow_point_earned(source_tower_id)` fires. That overflow point can later be spent on any node in, say, the support chain, substituting for a support-specific point — including choosing among *that* chain's still-locked-out options, since overflow is a wildcard for the point cost, not a wildcard past a node's own lock-out state.

## Edge Cases

- **`skill_unlocked`'s `source_tower_id` has no live tower at spend time.** The event's original purpose (`tower-mastery.md`: "identifies which on-screen tower instance triggered this update, for Mission HUD highlighting") cannot be satisfied when the firing context is a Sanctuary purchase — there is no live mission, no `tower_id`, nothing on screen to highlight. Resolution: `source_tower_id = -1` (sentinel, "no live tower context"). Mission HUD's existing `skill_unlocked` consumer (`tower-mastery.md` Dependencies: "unlock notifications") must tolerate `-1` gracefully — in practice this is moot, since Mission HUD isn't mounted at Sanctuary at all; only Hero Skill Build's library-add consumption (which never used `source_tower_id` for anything, only `skill_id`) and Encyclopedia's logging need to handle the sentinel.
- **A build signature keeps being mastered past its first threshold crossing.** This is not a special case — Formula 1's `floor(mastery_time / mastery_threshold_seconds)` naturally keeps producing new points at each subsequent whole multiple, `mastery_progress_updated` keeps firing clamped at 100% for HUD display purposes (unchanged from `tower-mastery.md` Rule 12), and `points_granted_count` simply keeps climbing alongside `points_earnable`. This is the *intended* primary income path (Rule 3), not a no-op.
- **All 4 nodes in a chain are already unlocked, hero keeps earning points in that archetype.** **Revised 2026-08-31**: this is no longer a dead end — Rule 3b converts every further point for that archetype into overflow instead. Formula 2's `all_nodes_unlocked` guard still makes a direct purchase attempt against a maxed chain an explicit, always-rejected, never-erroring no-op, but the *point itself* is never wasted; it becomes spendable elsewhere.
- **All 16 nodes across all 4 archetypes are unlocked — the entire tree is fully spent.** **Revised 2026-08-31, third pass** — this is the tree's genuine terminal state. From this point on, every further `skill_tree_point_earned` crossing (Tower Mastery's own emission never stops, per that document's Rule 14) matches no branch in Rule 3a/3b and produces no effect (Rule 3c) — `overflow_points` itself stops growing the instant the 16th node is purchased, since Rule 3b's own "at least one other archetype has a locked node" condition can no longer be true. A same-day gold-conversion design was tried and reverted here after a further review found it contradicted `resource-economy.md`, stacked unboundedly across simultaneously-mastered towers, and broke the Player Fantasy's permanence promise. Mastering towers past this point is an intentional, quiet no-op — the same "you've completed this" end-state pattern used elsewhere in the game, not a defect requiring a replacement reward.
- **Player has points in an archetype whose chain is fully unlocked, but 0 points in an archetype with locked nodes.** **Revised 2026-08-31**: this is now the exact scenario overflow points exist for. Once the maxed archetype's further mastery converts to overflow (Rule 3b), those overflow points can be spent on the archetype that still has locked nodes (Formula 2's `has_overflow` substitution). Archetype-specific pools themselves remain strictly non-fungible with each other (Rule 1/4) — only overflow, a separate wildcard pool, bridges them.
- **Hero dies mid-mission with unspent banked points (in any pool, including overflow).** No interaction — banked points are adventure-scoped state (Rule 1), not mission-scoped, and survive hero death exactly like already-unlocked skills do today (`hero.md` Rule 11's per-adventure persistence covers this GDD's state too, per Dependencies). See AC-6.
- **A save is loaded mid-Sanctuary-visit, between a node purchase's pool deduction and its unlocked-flag write.** These two mutations (Formula 2's pool/overflow deduction and `node.unlocked = true`) must be applied and persisted as a single atomic operation from Save & Persistence's perspective — never two separate `register()`-observable states a load could land between. This mirrors the same atomicity the existing Inventory/Equipment Forge rune-application path already requires (`equipment-forge.md`); no new precedent, but worth stating explicitly here since a partial application would either resurrect a spent point or unlock a node for free.
- **The player quits and relaunches mid-Sanctuary-visit, after spending this visit's 1 purchase.** **Corrected 2026-08-31, second pass** — `visit_spend_count` is now persisted (Rule 13), specifically to close this exact case: a relaunch restores the exact `visit_spend_count` value from the save file, not a fresh 0. If the visit's 1 purchase was already spent before quitting, it is still spent after relaunching — no further purchase is possible until a real mission is launched and the player returns. The prior version of this GDD left `visit_spend_count` ephemeral and accepted this as "an accepted, minor consequence" — `/review-all-gdds` found it was actually a free, zero-effort exploit (purchase → Save & Quit → relaunch → cap reset → purchase again, using nothing but an ordinary menu action) that defeated the entire per-visit cap, not a minor consequence.

- **Corrected 2026-08-31 — the cross-system atomicity claim in the prior draft was an overclaim, not a real guarantee.** An earlier version of this Edge Case asserted `skill_tree_points` and `points_granted_count` must commit as a single atomic operation. That's no longer even the right framing: after the ownership fix (Rule 3), `points_granted_count` lives entirely in Tower Mastery's own save blob (paired atomically with its own `mastery_time`, which it always was), and `skill_tree_points`/`overflow_points`/node-unlocked flags live entirely in this system's own save blob. **Atomicity is only claimed, and only needed, within each system's own blob** — exactly the same guarantee every other registered system gets from Save & Persistence, no more. If this system's own save data fails to restore, `save-persistence.md`'s standard `reset_to_defaults()` behavior applies (all 4 pools, overflow, and all 16 nodes reset together, internally consistent with each other) — this is the same category of accepted, standard data-loss risk every one of the 16 registered systems already carries on a corrupted save, not a bespoke problem this system needs its own reconciliation machinery for. What this system's own Formula 2 atomicity guarantee (the bullet above) still covers, unchanged: within one purchase, the pool/overflow deduction and the node's unlocked flag commit together.

- **A Choice node's non-selected options after purchase — the `LOCKED_OUT` state (new, 2026-09-01).** Once a Choice node is purchased, its unselected options move to `LOCKED_OUT`, a fourth node-option state distinct from `locked` (not yet reachable) and `unlocked` (chosen and active): `LOCKED_OUT` means permanently unreachable this playthrough, regardless of future point income in that archetype, and is never re-evaluated by Formula 2's purchasability check (a `LOCKED_OUT` option simply never appears as a candidate again). This is intentional, not a bug — it is the entire mechanical basis of the "which skill do you become" build-identity payoff `hero-skill-build.md`'s 2026-09-01 catalogue expansion introduces (2–3 real alternatives per Choice node, only one ever reachable per character). Sanctuary UI's spend screen (`sanctuary-ui.md` Core Rule 11) must render `LOCKED_OUT` options distinctly from ordinary `locked` ones — greyed-out-plus-lock-icon reads as "not yet," which is the wrong signal for "never, this character."
- **A save is loaded mid-Choice-node-purchase, between the chosen option's `skill_unlocked` emission and the siblings' `LOCKED_OUT` transition.** Both mutations are part of the same Formula 2 atomic operation this document's own Formula 2 Edge Case already covers (pool deduction, `node.unlocked = true`, and — as of this revision — the sibling lock-out loop, all committing together within this system's own save blob). No new atomicity mechanism is needed; this is the same guarantee, extended to cover one more field written in the same call.
- **A pre-revision save is loaded** (written before this GDD's Tower Mastery Rule 13 revision shipped) — see Dependencies' migration note. The save carries `_unlocked_skills: Dictionary[String, bool]` with no `points_granted_count` field populated for any `build_signature`. Resolution: absence of `points_granted_count[build_signature]` is treated identically to a value of 0 (not an error, not a crash) — all 4 archetype pools, overflow, and all 16 chain nodes (corrected 2026-08-31, second pass — was stated as 8) simply start at their fresh-game defaults (0 points, all locked), and `_unlocked_skills`' old data is read never again by any system. This is an explicit, intentional "no migration" outcome (Dependencies already scopes any richer shim as optional, out-of-scope future work) — this bullet exists so the *baseline*, un-shimmed behavior is itself specified and testable (see AC-12), not merely implied by omission.

## Tuning Knobs

| Knob | Current Value | Safe Range | Affects |
|---|---|---|---|
| Nodes per chain | 4 (fixed: `[Minor_1, Choice_1, Choice_2, Choice_3]`, revised 2026-09-01 for the Choice-node redesign — node *count* is unchanged from the pre-revision value, only node *type* composition changed) | 3–6 total, and the 3 Choice-node tier options (`opener`/`core`/`capstone`) must each stay non-empty in `hero-skill-build.md`'s catalogue for every archetype (currently 2 opener + 3 core + 3 capstone per archetype, 8 skills/archetype, 32 total) | Total playthrough-length investment per archetype, AND how many of `hero-skill-build.md`'s per-archetype skills are ever reachable by a single character (exactly 3 of 8, one per Choice node) — too few nodes trivializes the "sequence, not a moment" Player Fantasy, too many delays skill access unreasonably, and changing tier-option counts changes build diversity independent of node count |
| Point cost per node | 1 (fixed, uniform) | Could vary per node (e.g. Skill nodes cost 2) for a steeper curve | Pacing of chain completion relative to mastery-threshold pacing already tuned in `tower-mastery.md` |
| Minor node effect magnitude | Deferred (Group 4) | — | Whether Minor nodes feel like meaningful waypoints or filler — a content-authoring decision, not a structural one |
| Per-visit spend cap (Rule 13, new 2026-08-31) | 1 purchase per Sanctuary visit | 1–2 (2 would soften the sequencing decision toward "which two matter most," still meaningfully rationed; 3+ approaches the old uncapped behavior and should be treated as reopening the unreachable-fantasy defect this knob exists to close) | The entire mechanical basis of the Player Fantasy's "which path first" promise — this is the one knob that must never be removed or defaulted to unlimited without re-accepting that defect |

**Ratified pacing note (2026-08-31, re-review):** Interleaving 2 Minor nodes into each archetype's 4-node chain means reaching an archetype's 2nd (final) skill now costs roughly **double** the cumulative mastery-time investment compared to the pre-revision system, where each skill unlocked directly off its own threshold with no intervening spend. This is confirmed **intentional**, not an oversight — the added time is Minor-node content doing real pacing work (Group 4's "sequence, not a moment" is meant to cost something), not a wasted tax. No numeric retuning of `mastery_threshold_seconds` is needed to compensate; if playtesting later finds the combined pacing (Tower Mastery's threshold × this GDD's 4-node chain) too slow, retune `mastery_threshold_seconds` within its existing 20–90s range rather than changing chain length.

## Acceptance Criteria

1. **Revised 2026-08-31**: Crossing a whole multiple of a `build_signature`'s `mastery_threshold_seconds` (catalogued or not — the global `MASTERY_UNLOCK_THRESHOLD` applies when uncatalogued, per Formula 1) emits exactly 1 `skill_tree_point_earned(archetype, source_tower_id)` per crossing from Tower Mastery, unconditionally — never batched, and never itself mutating `skill_tree_points`. Tower Mastery never emits the old `skill_unlocked` directly, and never checks this system's chain-completion state before emitting.
2. A node is purchasable if and only if: `visit_spend_count == 0` for the current Sanctuary visit, its archetype pool OR the overflow pool has ≥1 point, AND it is the first locked node in its chain; attempting to purchase a locked-behind-a-predecessor node, a node with 0 available points (own pool and overflow both empty), or a second node in the same visit, is rejected without mutating any state.
3. **Revised 2026-09-01 for the Choice-node redesign.** Purchasing a `Choice` node deducts 1 point (from the archetype's own pool if available, else from overflow), marks the node unlocked, increments `visit_spend_count`, sets `node.chosen_skill_id` to the caller-supplied `player_selected_skill_id`, fires `skill_unlocked(chosen_skill_id, -1)` with the correct `skill_id`, and moves every other `skill_id` in `node.tier_skill_ids` into `node.locked_out_skill_ids` — verified for all 12 Choice nodes (3 × 4 archetypes) against `hero-skill-build.md`'s 32-skill catalogue, and verified that a purchase attempt whose `player_selected_skill_id` is not a member of `node.tier_skill_ids` is rejected without mutating any state (own pool, overflow, `visit_spend_count`, or the node itself).
4. Purchasing a `Minor` node deducts 1 point (own pool or overflow, same rule as AC-3), marks it unlocked, applies its effect, increments `visit_spend_count`, and fires `skill_tree_node_unlocked` — never fires `skill_unlocked`.
5. No node purchase is possible while `mission_phase` is `SCOUT`, `WAVE_ACTIVE`, `INTERMISSION`, `OUTCOME`, or `DEFEAT` — only at Sanctuary (corrected 2026-08-31 to include `OUTCOME`/`DEFEAT`, previously omitted).
6. Points earned mid-mission persist (banked) into the next Sanctuary visit, including points banked at the moment of hero death; a save/load cycle preserves both banked points (in every pool, including overflow) and unlocked-node state exactly, with no window in which a load can observe a single purchase's pool deduction without its corresponding unlocked-flag write, or vice versa, **within this system's own save blob** (revised 2026-08-31 — the cross-system atomicity claim against Tower Mastery's `points_granted_count` was an overclaim and has been removed; see Edge Cases).
7. Archetype pools never go negative and are never fungible with each other — spending physical points never reduces any other archetype's pool. Overflow is the sole exception by design (Rule 3b): it may substitute for any archetype's own point, but archetype pools never convert into overflow or into each other directly.
8. A new adventure (new game) resets all 4 archetype pools, the overflow pool, and `visit_spend_count` to 0, and all 16 nodes to locked — **revised 2026-09-01**: for the 12 `Choice` nodes this additionally means `chosen_skill_id` clears to empty and `locked_out_skill_ids` clears to an empty list, so every tier option is reachable again at the start of a fresh adventure, matching the existing per-adventure reset of skills.
9. Attempting a purchase in an archetype whose chain is already fully unlocked is rejected without error or state mutation, regardless of pool balance — verified this does not throw, crash, or attempt an out-of-bounds chain index (Formula 2's `all_nodes_unlocked` guard).
10. `skill_unlocked(skill_id, -1)` fired from a node purchase is consumed without error by both existing subscribers, Hero Skill Build and Encyclopedia — neither performs a live-tower lookup or highlighting action using the `-1` sentinel.
11. **Rescoped to this GDD's own implementation** (the original wording asserted a fact about `tower-mastery.md`'s codebase, which this GDD does not own and cannot gate a test on standalone — flagged by qa-lead review): the Skill Tree System's own code contains **exactly one** call site that emits `skill_unlocked` — the node-purchase path (Formula 2) — and no other. The companion assertion (that `tower-mastery.md`'s implementation has fully removed its own now-dead `skill_unlocked`-emitting branch, not merely made it unreachable) belongs on `tower-mastery.md`'s own Acceptance Criteria as a matching entry once that document's Rule 13 revision lands, per this GDD's "land-together" Notes — it is that document's test to own, not this one's.

12. Loading a save with `_unlocked_skills` populated (pre-revision data) and no `points_granted_count` entry for any `build_signature` does not error or block the load; all 4 archetype point pools and overflow initialize to 0 and all **16** chain nodes (corrected 2026-08-31 — was stated as 8, the Minor-node-only count, not the true total of 4 nodes × 4 archetypes) initialize to locked, exactly as a fresh game would, and `_unlocked_skills`' data is never read by this system (Edge Cases — Persistence Boundary migration case).

13. **New, 2026-08-31 — Per-visit spend cap.** Given `visit_spend_count == 0` and 2 or more archetypes each have a purchasable node, when the player purchases one, `visit_spend_count` becomes 1 and every other archetype's otherwise-purchasable node is rejected for the remainder of that Sanctuary visit; when `SANCTUARY` is next (re)entered, `visit_spend_count` resets to 0 and the previously-blocked purchase becomes available again.
