## Overview

Tarot Deck UI is the presentation layer for two Sanctuary-exclusive meta-progression systems — Tarot (deck composition, mission modifiers) and Hero Skill Build (active skill loadout, Ultimate derivation) — giving players a screen to compose their pre-mission strategic commitments before launching. Players interact with it directly and deliberately during every Sanctuary visit when they want to change their approach: swapping Tarot cards to reshape a mission's parameters, or reassigning skills to change which Ultimate their build produces. Without it, both systems' already-implemented gameplay logic has no player-facing surface — deck composition and skill assignment would be invisible, unchangeable choices baked in at data-authoring time rather than player decisions.

## Player Fantasy

**Signing Both Halves of a Prediction**

> This is the desk where you sign both halves of a single prediction about yourself — who you are today, and how far past your own line you dare stand on it — before a single wave gets to say whether you were right.

**Revision note (2026-07-24, post `/design-review`)**: The original draft of this section claimed the shell delivers this juxtaposition simply by hosting both screens "in one sitting" — but the design review found that claim unearned: Core Rule 1's mutual-exclusion model (only one screen ever on-screen at a time) is the literal opposite of "the same frame," and nothing in the original mechanics actually connected the two screens to each other. The fantasy now below is grounded in a real, added mechanic — Core Rule 7's **Current Build Snapshot** — rather than resting on the tab-switch alone.

Neither screen this shell hosts is a stranger by the time a player reaches this desk; each is a settled act performed a hundred times over. What this shell adds — concretely, not just tonally — is a small, persistent, read-only reminder of the *other* screen's headline commitment while the player works on either one: while composing a deck (Tarot), a Current Build Snapshot chip shows the Ultimate their current loadout derives; while composing a loadout (Hero Skill Build), the equivalent chip shows how much risk their current deck has already staked (Tarot's own aggregate speed/reward scalars). Neither chip is interactive and neither screen's own content changes — this is not the full simultaneous-panel model Sanctuary UI's own review found impossible to build, it is a single line of already-computed data borrowed from the other screen and displayed in this shell's own chrome. That is a small, honest amount of "juxtaposition" — enough that a player staging a deliberately harsh deck can glance up and see the Ultimate they're wagering it against, and enough that a player assembling their build can see, while doing it, how much they've already agreed to risk. It does not attempt the grander "the same answer, asked twice" claim the original draft made; that claim required both screens visible at once, which this shell's own structural model (peer, mutually-exclusive full-frame screens, same as Sanctuary UI's rooms) cannot support without abandoning that model entirely.

This section still deliberately does not re-argue either wrapped system's own Player Fantasy — `tarot.md` and `hero-skill-build.md` already each make their own case in full. What this shell owns is narrower than the original draft claimed: not the full juxtaposition of two complete self-portraits, but a legible, single-glance cross-reference between them, delivered by Core Rule 7, not by the tab strip alone.

**On order**: nothing here is hard-gated, but the natural reading runs downhill — identity is the premise, risk is the conclusion drawn from it. An *accurate* wager (Tarot's own fantasy explicitly distinguishes a wager from a gamble) can only be set once the player knows who they're bringing. "Build, then deck" is the default landing screen (Core Rule 2) for that reason — but this is a **flagged hypothesis, not settled design reasoning** (see OQ-3): it is a permanent default applied on every single entry with no persisted memory of last-used screen, which is a real, repeated cost for any player who prefers Tarot first, not merely a soft nudge. It should be validated against actual playtest behavior before being treated as confirmed.

## Detailed Design

### Core Rules

**Core Rule 1 — Structural Model: A Sibling Shell, Not a Sanctuary UI Room**
Tarot Deck UI is its own top-level destination, architecturally separate from `sanctuary-ui.md`'s 5-room hub (which wraps only Inventory+Crafting, Menagerie, Defense Building, and Equipment Forge — neither Tarot nor Hero Skill Build appear in that GDD's room list, dependency table, or Interactions table, and this GDD's own two wrapped systems' Interactions tables likewise never mention Sanctuary UI). It hosts exactly 2 full-frame screens — Tarot's deck-building screen (`tarot.md`'s own complete UI Requirements) and Hero Skill Build's loadout screen (`hero-skill-build.md`'s own complete UI Requirements) — plus a thin persistent chrome layer, structurally the smallest possible version of the shell problem Sanctuary UI solved: 2 peer-register screens instead of 4 differently-shaped ones, so no diorama-visibility problem exists here at all — there is no third "overview" content state, only the 2 screens and the chrome connecting them.

**Core Rule 2 — Navigation: 2-Screen Tab Strip, Same Trigger/Bumper Split as Sanctuary UI**
A fixed 2-entry tab strip (Hero Skill Build · Tarot Deck — in that order, matching the Player Fantasy's "build, then deck" natural reading, though either is directly selectable at any time) lists both screens, always visible.
- **K/M**: click either tab directly.
- **Gamepad/keyboard**: `LT`/`RT` (or `[`/`]`) switch between the 2 screens. **Not** `LB`/`RB` — both wrapped screens already commit those to their own internal category-cycling (`tarot.md`: "Shoulder buttons (LB/RB) cycle card pool categories"; `hero-skill-build.md`: "shoulder buttons cycle the library's archetype-category filter"). Reusing `LB`/`RB` for screen-switching here would reintroduce the exact ambiguity `sanctuary-ui.md`'s Core Rule 2 already identified and fixed for its own room switching — this GDD reuses that same fixed split (**triggers = switch screens, bumpers = switch categories within the open screen**) rather than inventing a second, incompatible convention for the same physical inputs elsewhere in the same game.
- No onboarding tooltip is needed for this specific split — a player who has already used Sanctuary UI (the far more complex 5-room instance of the identical trigger/bumper convention) has already learned it; this shell is downstream of that learning, not a first exposure to it.

**Core Rule 3 — Entry: Sanctuary UI's Dedicated Loadout Affordance (Revised — Closes a Real Gap the Review Found)**
The shell is reached via **Loadout**, the tab strip's 6th entry in Sanctuary UI (`sanctuary-ui.md` Core Rule 2/10, redesigned 2026-07-24 — **updated here to match; this document's own prior text described an earlier, since-superseded version of that mechanism**). Loadout is selectable from **any** Sanctuary UI state — `OVERVIEW` or any `ROOM_*` — not `OVERVIEW`-only; selecting it tears down whatever room is currently active (if any) and hands off to this shell. This is a genuine improvement over the original OVERVIEW-only framing: a player already deep in, say, Defense Building doesn't need to detour through `OVERVIEW` first to reach their loadout.

**Core Rule 4 — Exit: Return to Sanctuary**
A Cancel/back action (consistent with both wrapped screens' own established Cancel idiom) or an explicit "Return to Sanctuary" affordance closes the shell and returns control to Sanctuary UI, which mounts a fresh instance at `OVERVIEW` (per `sanctuary-ui.md` Core Rule 5 and Core Rule 10's own stated return path) — not a special-cased "return from Loadout" state, the same entry path any other Sanctuary arrival uses. No confirmation of any kind is required (Core Rule 5 explains why) and no EventBus event fires on this transition beyond whatever internal signal Sanctuary UI itself needs for its own remount — the same "internal navigation is silent, only genuine hand-offs are observable" principle `sanctuary-ui.md` Core Rule 8 already establishes for its own Launch/Depart.

**Core Rule 5 — Lifecycle: Destroy-and-Recreate on Screen Switch; No Staged State Exists to Protect**
Each of the 2 screens is instantiated fresh as a child of a shell-owned `ScreenHost` `Control` on entry, and freed on exit (screen switch or shell exit) — the same destroy-and-recreate model `sanctuary-ui.md` Core Rule 6 adopted for its own rooms, reused here for the identical reason (guaranteed `_ready()` re-fire, zero stale-subscription risk). **Restated explicitly here, not just cited by reference** (the design review found the original draft only pointed at `sanctuary-ui.md`'s own mechanism without restating it, which a programmer working from this file alone would miss): each exit synchronously calls `set_process_unhandled_input(false)` on the outgoing screen before `queue_free()`-ing it, closing the same same-frame double-input-handling gap `queue_free()`'s end-of-frame deferral would otherwise allow — identical mechanism, independently restated. Unlike Sanctuary UI's rooms, however, **this lifecycle has almost no discard-related edge case to design around** for the two screens' own primary content: both `tarot.md` ("Deck-editing confirmation step — none required... a drag/drop or select-confirm-select-confirm swap simply applies immediately") and `hero-skill-build.md` ("there is no separate 'preview vs. commit' state... every slot and sub-slot change takes effect immediately") confirm every *committed* edit on both screens is already fully applied, fully reversible, and zero-cost the instant it happens. **One real transient exception exists and is addressed explicitly** (the design review found the original draft's blanket "nothing to lose" claim didn't actually account for it): `hero-skill-build.md`'s own gamepad flow has an in-progress "pick-up" state (a library entry selected, not yet placed in a slot) between the first and second confirm presses. A screen switch mid-pick-up abandons that in-progress selection — this is safe for the same reason Cancel is safe (no model mutation has occurred yet, since only the second confirm commits anything), not because of the "already committed" reasoning that covers every other edit on both screens. No toast or confirmation affordance is needed either way (unlike Sanctuary UI's "staged changes discarded" toast, which exists specifically because Equipment Forge/Defense Building's staged actions represent real lost UI effort) — an abandoned pick-up is a single unconsummated selection, not multi-step staged work.

**Core Rule 6 — The Tarot/Mission-Select Conflict Indicator (Revised — Fixes a Real Bug the Review Found)**
`tarot.md` Rule 8 explicitly assigns this shell responsibility: when a slotted Tarot card's effect targets the same underlying mission parameter as an active Mission Select run modifier, the Tarot screen (not a shell-level element — only Tarot's own screen has the `source_card_id` context and the read-only `run_modifier_selected` subscription `tarot.md` already grants it) renders a small, distinct badge anchored to the conflicting tray slot's top-right corner, offset 4px outside the slot's own bounding box so it never occludes the card's own lock-state or mastery-pip iconography.

**The match is a conceptual mapping, never a literal string comparison** — the design review found the original draft specified `modifier_type == modifier_id`, which is a bug: `tarot.md`'s 4 registered `modifier_type` values (`tarot_speed_scalar_mult`, `tarot_reward_scalar_mult`, `tarot_difficulty_growth_rate`, `tarot_wave_config_override`) and `mission-select.md`'s actual `run_modifier_selected.modifier_id` catalogue (`"extend_waves"`, `"difficulty_growth_boost"`) are disjoint string vocabularies — that comparison could never match, making the indicator permanently inert as originally specified. The real, intended mapping (both parties target the same underlying `WaveConfig` field, confirmed against each system's own Formulas sections):

| Tarot `modifier_type` | Conflicts with Mission Select `modifier_id`(s) | Shared target |
|---|---|---|
| `tarot_difficulty_growth_rate` | `"difficulty_growth_boost"` | Both write to `WaveConfig.difficulty_growth_rate` (`r`) — Tarot via REPLACE, Mission Select via an additive request Wave Manager resolves |
| `tarot_wave_config_override` | `"extend_waves"` **and** `"difficulty_growth_boost"` | A whole-`WaveConfig` swap replaces every field the swapped-in config defines, including `difficulty_growth_rate` — so this `modifier_type` conflicts with *both* Mission Select modifiers, not only the wave-count one. **(Corrected during independent re-verification, 2026-07-24 — the first-pass table only mapped this row to `extend_waves`, missing that a whole-Resource REPLACE necessarily also touches `r`.)** |
| `tarot_speed_scalar_mult` | *(none)* | No current Mission Select analog — this `modifier_type` can never trigger the indicator today |
| `tarot_reward_scalar_mult` | *(none)* | Same — no current Mission Select analog |

A card can therefore show conflict badges against more than one active Mission Select selection simultaneously (only possible for `tarot_wave_config_override`, since Mission Select's own catalogue is presently 2 mutually-independent modifiers) — the badge and inspect text (below) must handle a multi-conflict card, not assume exactly one. This table is this shell's own explicit constant, not inferred at runtime from string similarity. If Mission Select's `modifier_id` catalogue grows, this table needs a corresponding entry — flagged as a maintenance note in Tuning Knobs.

**Stale-value clearing (also fixed — the review found this asserted without a mechanism)**: `run_modifier_selected` values are Mission Select's own per-session state, reset by Mission Select itself whenever it transitions to a fresh `CONFIGURING` state for a new mission (per `mission-select.md`'s own state model) — the conflict indicator's "no stale conflict from a prior mission" guarantee (Edge Cases) holds because it reads Mission Select's *current* live value at every render, never a cached one, and Mission Select's own lifecycle (not this document's) is what guarantees that value is fresh. This document does not own or duplicate that reset logic — it depends on it, and states the dependency explicitly rather than asserting the outcome without naming the mechanism.

On inspect, plain text names the exact shared target field and which Mission Select selection collides with it — the coupling is never icon-only at that tier, mirroring `tarot.md`'s own existing rule for its risk/reward modifier disclosure. The indicator is purely advisory: it never blocks navigation, screen-switch, or shell exit, and `tarot.md` Rule 8 grants it no authority over mission launch or modifier resolution (that remains Wave Manager's territory) — it exists only so the player can see the overlap before committing, not to adjudicate it.

**Core Rule 7 — Current Build Snapshot: The Shell's Actual Cross-Screen Bridge (New — Added to Close the Review's Central Finding)**
The design review's most serious finding was that this shell's Player Fantasy claimed a "juxtaposition" the original mechanics never delivered — two mutually-exclusive screens with no signal connecting them. This rule adds a small, bounded, genuinely cross-screen element rather than abandoning the fantasy: a persistent, read-only **Current Build Snapshot** chip lives in this shell's own chrome (not inside either wrapped screen's own layout, so neither `tarot.md` nor `hero-skill-build.md` needs to change) and shows a one-line summary of the *other* screen's current headline state:
- While `TAROT_DECK` is active: the chip shows Hero Skill Build's currently-derived `ultimate_id` (already-computed data, per `hero-skill-build.md`'s own Formula — this rule reads it, never computes it).
- While `HERO_SKILL_BUILD` is active: the chip shows a compact readout of Tarot's own current aggregate risk (`tarot_speed_scalar` and/or the equipped-card count, already-computed data per `tarot.md`'s own Formula F4 — again read, never computed here).

Both directions are pure reads of state each wrapped system already derives for its own purposes — this rule introduces no new formula, no new EventBus event, and no new data ownership; it only adds a display surface in the shell's own chrome. The chip is never interactive (consistent with Core Rule 3's persistent-resource-header precedent from `sanctuary-ui.md`) and updates live as either screen's underlying state changes, without requiring a screen switch to refresh. This is the mechanic the revised Player Fantasy section actually grounds itself in — a small, honest amount of "seeing the other half of the prediction while composing this one," not the larger simultaneous-panel claim the original draft implied but could not structurally support.

## Formulas

None. Tarot Deck UI is a pure presentation/navigation shell — it defines no calculation of its own; every value either wrapped screen displays, including Core Rule 7's Current Build Snapshot chip, is that screen's own already-defined data (Tarot's `effective_modifier_value`/`tarot_speed_scalar`, Hero Skill Build's derived `ultimate_id`), and the shell's own behavior (screen switching, entry/exit, the conflict indicator's mapped-match check, the snapshot chip's read-and-display) is state transition, table lookup, and display logic, not a derived formula. This matches `sanctuary-ui.md`'s and `mission-hud.md`'s own identical precedent for the same reason.

## Edge Cases

- **If the player switches from one screen to the other mid-edit**: no confirmation or save prompt of any kind — the prior screen's committed edit already applied immediately (Core Rule 5), so there is nothing pending to lose or commit.
- **If the player switches screens (or exits the shell) while a Hero Skill Build gamepad "pick-up" is in progress** (a library entry selected but not yet placed, per `hero-skill-build.md`'s own 2-step confirm flow): the in-progress selection is abandoned, same outcome as pressing Cancel — safe because no model mutation has occurred yet (Core Rule 5's transient-state note), not because the selection was "already committed."
- **If the player enters the shell with 0 unlocked Tarot cards**: the Tarot screen shows its own already-designed 0-card library/pool state; shell navigation to it remains available regardless — it is gated only by phase state (Core Rule 3's entry path), never by content availability.
- **If the player enters the shell with 0 skills yet learned via Tower Mastery**: the Hero Skill Build screen shows its own already-designed empty-library state; shell navigation to it remains available for the same reason as above. The Core Rule 7 snapshot chip on the Tarot screen shows `ultimate_id = EMPTY` in this case (Hero Skill Build's own defined value for "fewer than 4 slots filled"), not a blank/error state.
- **If Mission Select has made no `run_modifier_selected` selection yet when the Tarot screen opens**: the conflict indicator (Core Rule 6) shows no conflict for any slotted card — this is not an error state. Stale-conflict prevention is guaranteed by Mission Select's own `CONFIGURING`-state reset lifecycle (Core Rule 6), not by any logic this document owns.
- **If a slotted Tarot card's `modifier_type` has no entry in Core Rule 6's mapping table** (`tarot_speed_scalar_mult`, `tarot_reward_scalar_mult` — currently no Mission Select analog): the conflict indicator never fires for that card, by design — this is not a missing case, it is the mapping table's own explicit "no analog" row.
- **If the player attempts to reach this shell while a mission is active** (Tarot `LOCKED`, Hero Skill Build `LOCKED` per each system's own state model): shell entry is blocked at the Sanctuary-navigation level — this is inherited from the underlying phase model (the same gate Sanctuary UI itself is subject to), not a shell-internal edge case this document invents.
- **If the player triggers shell exit while the conflict indicator is actively showing a conflict**: exit proceeds unconditionally — the indicator is advisory only (Core Rule 6), never a blocking state, matching `tarot.md` Rule 8's own explicit statement that it grants the indicator no authority over launch or navigation.
- **If a slotted card's `modifier_type` maps to `tarot_wave_config_override` and Mission Select's `"extend_waves"` is also active**: the conflict indicator fires per Core Rule 6's mapping table row for that pairing — the table is symmetric in that both a REPLACE-type Tarot modifier and Mission Select's additive request can collide on the same underlying `WaveConfig` field; the indicator flags the overlap without adjudicating which one wins (that resolution logic belongs to Wave Manager, per `tarot.md` Rule 7, not to this UI).

## Visual/Audio Requirements

**Shell chrome visual language**: reuses Mission HUD's and Sanctuary UI's own established screen-space language wholesale — chamfered-rectangle shape grammar, UI Chrome/Parchment/Accent palette, flat single-inset-shade iconography, same motion contract (snappy-in ≤120ms / eased-out settle 150–200ms, no overshoot). This is the third system in this project to need this exact property (chrome is a frame, not a painting), and the third time it is reused rather than reinvented.

**Screen-switch transition**: a literal drawer-slide between the 2 screens, horizontal only, matching Sanctuary UI's own room-switch treatment — one consistent physical axis across every screen-switching shell in this project, not a per-document bespoke transition.

**Conflict indicator badge**: a small warning-glyph badge (a shape reserved exclusively for this purpose — never reused from the lock-state silhouette or mastery-pip iconography already active on the same card, per Core Rule 6) anchored 4px outside the conflicting tray slot's top-right corner (Tuning Knobs). Non-color-first: the glyph shape alone communicates "conflict" with color as confirmatory only, matching this project's standing Sec 4.5-equivalent colorblind discipline.

**Current Build Snapshot chip**: a single-line, non-interactive text+icon readout docked in the shell's own chrome (not inside either wrapped screen's own layout), reusing the persistent-resource-header's visual treatment from `sanctuary-ui.md` (UI Chrome background / UI Parchment text, zero interactive affordance, no focus ring) — the project's established "read-only cross-reference" register, not a new visual language. On `TAROT_DECK`, shows Hero Skill Build's `ultimate_id` (or a plain "No Ultimate yet" state when `EMPTY`); on `HERO_SKILL_BUILD`, shows Tarot's aggregate risk readout. Updates with the same scale-pop feedback already established for the resource header and Connection Badges, live as the underlying value changes — never requiring a screen switch to refresh.

**Tab strip icons**: 2 icons — Hero Skill Build (a stylized Ultimate-glyph silhouette, distinct from any individual skill-category icon already established in `hero-skill-build.md`, so the tab reads as "the loadout as a whole," not any one archetype) and Tarot Deck (the literal tarot-card-back motif already established in `tarot.md`'s own Visual/Audio Requirements as this system's "wizard's cabinet" anchor — directly reused, not reinvented).

**Audio**: no `design/audio/` bible exists yet for this project (matching every prior GDD's already-flagged gap) — directional only. Screen-switch reuses the same restrained "Contemplative" SANCTUARY-energy cue category `sanctuary-ui.md` specifies for its own room switches; the conflict indicator's arrival wants a subtle, non-alarming notice tone (this is advisory information, not an error) distinct from either wrapped screen's own denial/lock-interaction sting. Specific SFX selection deferred until audio direction exists.

## UI Requirements

This shell's own structural layout (tab strip, screen-switch transition, entry/exit, the conflict indicator's placement and glyph, the Current Build Snapshot chip) is fully specified in Detailed Design (Core Rules 1–7) and Visual/Audio Requirements above. **The two screens' own internal layout, interaction model, component inventory, and accessibility commitments are NOT re-specified here** — `tarot.md`'s and `hero-skill-build.md`'s own "UI Requirements" sections are each already complete, standalone full-screen specifications (deck tray + fanned card pool + drag-drop/select-confirm gamepad model for Tarot; library panel + 4 active slots + Ultimate readout for Hero Skill Build) and remain the sole source of truth for their own screens' content **as design text — neither screen exists as an actual `.tscn` file yet, per OQ-5**. This document's job is strictly the shell around them, per Core Rule 1, plus the one cross-screen bridge Core Rule 7 adds.

What remains for a dedicated UX spec (`design/ux/tarot-deck-ui.md`, not yet authored): the shell-level ASCII wireframe (tab strip + whichever screen is active), the exact tab-strip icon assets (named at concept level above), and the conflict-indicator badge's exact glyph design — everything else a UX spec would normally need for the 2 screens themselves is already covered by `tarot.md`'s and `hero-skill-build.md`'s own UI Requirements sections and does not need re-deriving here.

## Acceptance Criteria

Scoped strictly to the shell — navigation, entry/exit, and the conflict indicator. **Neither wrapped screen's own internal behavior is re-tested here**; `tarot.md`'s and `hero-skill-build.md`'s own extensive Acceptance Criteria sections already cover deck-building and loadout-assembly behavior in full, and duplicating that coverage here would create two sources of truth for the same behavior.

### Group 1 — Core Rules 1–2: Structural Model and Navigation

- [ ] **GIVEN** the shell has just mounted, **THEN** exactly 2 states exist (`HERO_SKILL_BUILD`, `TAROT_DECK`) and the tab strip is present and rendering in both.
- [ ] **GIVEN** either state is active, **WHEN** the other tab is clicked (K/M) or `LT`/`RT`/`[`/`]` is pressed, **THEN** the active state switches accordingly.
- [ ] **GIVEN** `TAROT_DECK` is active, **WHEN** gamepad `LB`/`RB` is pressed, **THEN** the shell's active state does **not** change — confirming bumpers never trigger a screen switch, mirroring `sanctuary-ui.md`'s identical AC for its own rooms. **(Rewritten per design review — the original phrasing also asserted what `LB`/`RB` *does* inside Tarot's own screen, which is `tarot.md`'s own AC territory, not this shell's; this AC now asserts only the shell-owned half.)**

### Group 2 — Core Rule 3: Entry

- [ ] **GIVEN** the player is at any Sanctuary UI state — `OVERVIEW` or a `ROOM_*` state (updated per `sanctuary-ui.md`'s Core Rule 10 redesign, which made Loadout reachable from anywhere, not `OVERVIEW`-only), **WHEN** the Loadout tab is selected, **THEN** this shell opens, defaulting to `HERO_SKILL_BUILD` (Player Fantasy's "build, then deck" ordering, flagged provisional per OQ-3).
- [ ] **GIVEN** the shell was previously exited (via Cancel or the explicit return affordance) while `TAROT_DECK` was the active state, **WHEN** the shell is re-entered via a fresh Loadout selection, **THEN** it defaults to `HERO_SKILL_BUILD` again, not the last-used screen — confirming the default is a genuine fixed default, not accidentally sticky session state. **(Added per design review — the original AC set only tested a fresh first mount, not this recurrence case, despite OQ-3 explicitly raising "last used screen" as a live alternative.)**
- [ ] **GIVEN** a mission is currently active (Tarot `LOCKED`, Hero Skill Build `LOCKED`), **WHEN** the player attempts to reach this shell, **THEN** entry is unavailable — inherited from the underlying phase gate, not a shell-specific check.

### Group 3 — Core Rule 4–5: Exit and Lifecycle

- [ ] **GIVEN** the shell is open in either state, **WHEN** Cancel/back or the explicit return affordance is triggered, **THEN** control returns to a freshly-mounted Sanctuary UI instance at `OVERVIEW`, with no confirmation prompt of any kind.
- [ ] **GIVEN** either screen has just received a player edit (e.g. a Tarot card swap, a Hero Skill Build slot assignment) that each wrapped screen's own GDD defines as immediately committed, **WHEN** the player immediately switches to the other screen or exits the shell, **THEN** re-entering that screen (or querying its own already-existing state, per `tarot.md`'s/`hero-skill-build.md`'s own AC suites) shows the edit still applied. **(Reframed per design review — the original AC risked reaching into Tarot's/Hero Skill Build's own internal state, which this document explicitly says it doesn't own; this version verifies the same claim through each screen's own already-existing, already-owned state query instead of inventing a new shell-level assertion about internal data.)**
- [ ] **GIVEN** a Hero Skill Build gamepad pick-up is in progress (a library entry selected, not yet placed), **WHEN** the player switches screens or exits the shell, **THEN** the pick-up is silently abandoned with no error, no toast, and no lingering "picked up" visual state on next entry.

### Group 4 — Core Rule 6: Conflict Indicator

- [ ] **GIVEN** a slotted Tarot card's `modifier_type` has a mapped entry in Core Rule 6's table (`tarot_difficulty_growth_rate` or `tarot_wave_config_override`) and Mission Select's active `run_modifier_selected` targets that mapped pairing, **WHEN** the `TAROT_DECK` state is active, **THEN** the conflict badge renders on that card's tray slot. **(Corrected per design review — the original AC asserted a direct `modifier_type == modifier_id` match, which is impossible given the two systems' actual disjoint string vocabularies; this AC now tests the real mapped-pairing behavior.)**
- [ ] **GIVEN** a slotted Tarot card's `modifier_type` is `tarot_speed_scalar_mult` or `tarot_reward_scalar_mult` (no mapping-table entry exists), **THEN** no conflict badge ever renders for that card regardless of Mission Select's current selection — confirming the "no analog" rows are a real, tested absence, not just documented prose.
- [ ] **GIVEN** no `run_modifier_selected` value is currently set, **WHEN** `TAROT_DECK` is active, **THEN** no conflict badge renders for any slotted card.
- [ ] **GIVEN** the conflict badge is showing, **WHEN** the player navigates to `HERO_SKILL_BUILD` or exits the shell, **THEN** the transition proceeds without being blocked or gated by the indicator.
- [ ] **GIVEN** the conflict badge is showing and the player inspects the affected card, **THEN** plain text names the exact shared `WaveConfig` target field and the colliding Mission Select selection — never icon-only at that tier.

### Group 5 — Core Rule 7: Current Build Snapshot

- [ ] **GIVEN** `TAROT_DECK` is active, **THEN** the snapshot chip displays Hero Skill Build's current `ultimate_id`, or an explicit "No Ultimate yet" state when `ultimate_id == EMPTY`.
- [ ] **GIVEN** `HERO_SKILL_BUILD` is active, **THEN** the snapshot chip displays Tarot's current aggregate risk readout, reflecting the currently-equipped deck.
- [ ] **GIVEN** either screen's underlying derived value changes while the *other* screen is active (e.g. a prior Hero Skill Build slot edit changes `ultimate_id`, observed while now on `TAROT_DECK`), **THEN** the snapshot chip reflects the change without requiring a screen switch to refresh.
- [ ] **GIVEN** the snapshot chip is focused via keyboard/gamepad navigation attempt, **THEN** it never receives focus and shows no focus ring — confirming it is not a navigable region, matching the resource-header precedent it reuses.
