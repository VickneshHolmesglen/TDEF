## Overview

The Pathfinding System computes and serves navigable routes from monster spawn cells to goal cells across the mission grid. It is the single authority on walkable paths — the Monster System calls it directly to retrieve a pre-computed path at spawn and again whenever a tower placement invalidates a monster's current route. Rather than computing a fresh path for every monster independently, the system maintains a small set of **route templates**: one cached `Array[Vector2i]` path per SPAWN cell to the nearest reachable GOAL cell. Monsters share these templates; `get_path(from_cell, tier)` returns the template's tail from `from_cell` onward in O(1) time, placing no per-monster computation overhead on the critical path during `WAVE_ACTIVE`. When the player places or removes a tower, the affected cells change walkability; the system rebuilds only the route templates whose paths pass through those cells, then emits `path_invalidated` so active monsters can refresh their local copies. At MVP, the tier parameter is reserved for future agent-type differentiation (e.g., flying monsters) — all tiers use the same walkability rules. The system depends only on the Grid; it is an Autoload, and all consumers read from it via direct function call. Without it, monsters have no navigable routes, towers cannot form functional chokepoints, and the game's spatial strategy layer collapses entirely.

## Player Fantasy

The Pathfinding System is silent infrastructure — it has no player fantasy of its own. What this system delivers in isolation is correct, optimal, silent re-routing: every tower placement produces the geometrically correct new path for every monster, within one deferred frame. This is necessary but not sufficient for the player experience of "the battlefield listened."

The full fantasy — where the player commits a tower and the horde visibly peels along the new line they drew — requires two companion systems that are not yet designed:

1. **Mission HUD route-preview overlay (pillar-critical dependency):** For "Placement is the Puzzle" to deliver its fantasy, a route-preview overlay should subscribe to `path_invalidated` and render an updated route line during SCOUT and INTERMISSION. This is a consumer-agnostic signal contract — whether the overlay exists, what it looks like, and its interaction design are Mission HUD GDD concerns. **Signal contract for any overlay implementation:** On receipt of `path_invalidated`, the consumer must call `get_path(Grid.get_spawn_cells()[0], 0)` (at MVP: single SPAWN cell, tier=0) to obtain the updated route. `affected_cells` in the payload is the union of tower footprint cells that changed walkability — it is NOT the new route; rendering it directly as a route line would display the tower placement footprint instead of the navigation path. The overlay must not attempt to re-render during WAVE_ACTIVE (placement is locked; the route cannot change). Whether the overlay renders during PRE_WAVE is at the Mission HUD's discretion — templates are stable in PRE_WAVE but `path_invalidated` does not fire in that phase, so the last INTERMISSION update remains current.

2. **Art Bible: PLACEABLE terrain visual treatment (required for "Placement is the Puzzle" legibility):** Unoccupied PLACEABLE cells are traversable at elevated cost (Rule 17, cost = 10). Players must be able to distinguish "this cell is buildable but monsters can cross it" from "this cell has a tower blocking passage." Without a distinct visual treatment, monster routing through an unoccupied PLACEABLE cell reads as "the monster cheated through my tower" — an unattributable outcome that undermines the mastery framework the pillar depends on.

The chokepoints that hold, the lanes that funnel correctly, the BOSS that routes around the wall the player built — these depend on the Pathfinding System being correct AND on the companion systems making that correctness visible. This GDD specifies the routing contracts; the player-facing delivery is owned by Mission HUD and Art Direction.

## Detailed Design

### Core Rules

**I. System Identity**

1. The Pathfinding System is an Autoload singleton. All consumers call it via direct function call — not via EventBus.
2. Active during all mission phases. Idle between missions.
3. At MVP, one routing mode exists: SPAWN cell → nearest GOAL cell, cardinal-only movement. **MVP missions use exactly one SPAWN cell.** The Voronoi partition code is **MVP scaffolding only** — the Chebyshev-distance assignment is geometrically nearest SPAWN, NOT cost-nearest. At MVP (N=1 SPAWN) this is a no-op: all walkable cells assign to the single SPAWN. Multi-SPAWN support requires replacing this with reverse-Dijkstra flood-fill from each SPAWN's template, plus rebuilding `_spawn_assignment` in the dirty-template pipeline (tracked as OQ-[post-MVP]). Do not author multi-SPAWN missions expecting the current Voronoi code to route correctly — it will not. Missions with more than one SPAWN cell must not ship for MVP.
   **CI enforcement gate (mandatory):** The mission map validator (AC-13) must include a check: if a mission's GridConfig contains more than one SPAWN cell, validation fails with error: `"Multi-SPAWN mission requires path-cost Voronoi (reverse-Dijkstra) — Chebyshev assignment is incorrect for N>1 SPAWN cells (cells near walls between SPAWNs are silently misassigned; fallback A* masks the error as performance degradation). Do not author multi-SPAWN missions until OQ-[post-MVP] is resolved."` This gate prevents the Chebyshev fallback-masking defect from reaching playtest.
   **Code-spec TODO (binding):** The `_compute_spawn_assignment()` function must contain the comment: `# TODO(post-MVP): Replace with reverse-Dijkstra flood-fill. Chebyshev distance produces incorrect assignment for cells near walls between SPAWNs — fallback A* masks the misassignment as performance degradation, not a routing failure. See pathfinding.md Rule 3.`

**II. Route Templates**

4. The system maintains one **route template** per SPAWN cell: a cached `Array[Vector2i]` path from that SPAWN cell to the nearest reachable GOAL cell.
5. Templates are built once at the start of `SCOUT` phase, after the Grid receives its `GridConfig` — before the player places any tower. **Precondition:** `Grid.get_spawn_cells()` must return ≥1 cell and `Grid.get_goal_cells()` must return ≥1 cell. If either returns empty, template initialization calls `push_error("PathfindingSystem: mission map has no SPAWN or GOAL cells — templates not built")` and no templates are built. After all N templates are built, the system sets `_templates_built: bool = true` and emits `templates_ready(spawn_count: int, build_duration_ms: float)` via EventBus. Wave Manager must subscribe to `templates_ready` and must not emit `monster_spawn_requested` before this event fires. `_templates_built` is reset to `false` on mission restart (Rule 21) and remains `false` if the precondition guard fires (no SPAWN or GOAL cells).
   **Trigger mechanism:** PathfindingSystem subscribes to `mission_phase_changed` (EventBus). On receipt, if `new_phase == "SCOUT"`, template initialization runs immediately. Templates do NOT build in `_ready()` — the EventBus subscription is the sole trigger, ensuring templates always build after the Grid has received its `GridConfig` for the current mission (including on DEFEAT → SCOUT restart). *(ADR-0004's architecture diagram incorrectly labels this step as `Pathfinding._ready()`. That diagram will be corrected to reference `mission_phase_changed` as the build trigger.)*
   **Distinction from Rule 7 (`path = []` case):** `_templates_built = true` is set whenever template initialization completes normally — including when individual templates store `path = []` (no route exists for that SPAWN). The only time `_templates_built` remains `false` after a SCOUT event is when the Rule 5 precondition guard fires (no SPAWN or GOAL cells in the GridConfig at all) and exits before building any templates. These two outcomes are observably distinct: (a) when `_templates_built = true` and a template has `path = []`, `get_path()` flows through template lookup → `cell_index_map` miss → fallback A* → sets `last_fallback_warning`. (b) when `_templates_built = false`, `get_path()` exits at the pre-init guard (Rule 15a) without ever setting `last_fallback_warning`. AC-11 is only testable if this distinction is correctly implemented — an implementor who conflates the two cases by leaving `_templates_built = false` after a Rule 7 no-path result will break `last_fallback_warning` observability silently.
6. Each template stores two structures:
   - `path: Array[Vector2i]` — ordered cells from SPAWN to GOAL
   - `cell_index_map: Dictionary[Vector2i, int]` — maps each cell in the path to its index (O(1) membership lookup)
7. When A* finds no path from a SPAWN cell to any GOAL cell, that template stores `path = []`. `get_path()` returns `[]` for that SPAWN cell.

**5b. `_spawn_assignment` population and lifecycle (binding):** `_spawn_assignment: Dictionary[Vector2i, Vector2i]` (walkable cell → nearest SPAWN cell coordinate) is populated immediately after all N route templates are built, as part of the same SCOUT-phase initialization block — before `templates_ready` emits. It is NOT rebuilt during dirty-template rebuilds (Rule 13); it remains stable for the entire mission because SPAWN cell coordinates are fixed in the GridConfig for a given mission. If `get_path()` is called before `_spawn_assignment` is populated (pre-init race), the `_templates_built == false` guard (Rule 15a) intercepts the call and returns `[]` — `_spawn_assignment` is empty at that point, and the pre-init guard fires before any lookup is attempted. `_spawn_assignment` is cleared to `{}` on mission restart (Rule 21) alongside `_templates_built` reset. These two fields are always cleared and rebuilt together — any implementation that resets one without the other produces an inconsistent state where `_templates_built == true` but `_spawn_assignment` is empty (or vice versa).

**5a. SPAWN cell placement exclusion (mandatory constraint):** SPAWN cells are always walkable (cost = 1, Rule 17) and must never appear in a tower footprint. The Grid must reject any `place_tower()` call whose footprint contains a SPAWN cell. The Tower System must not submit SPAWN cells as valid placement targets. Violating this constraint causes the SPAWN's template origin to become non-walkable, removing `spawn_cell` from `cell_index_map` — every monster spawning at that cell fires fallback A* on every spawn permanently, with no loud failure signal.

**III. Multi-GOAL Routing**

8. When multiple GOAL cells exist, a virtual **super-goal node** is inserted into the AStar2D graph connected to every real GOAL cell with zero-cost edges. A* runs to the super-goal ID. The super-goal node is stripped from the returned path before storage. This finds the nearest reachable GOAL cell in a single A* pass with no per-GOAL runs.
   - **point_id:** `super_goal_id = grid_cols * grid_rows`. The last valid real cell ID is `(grid_rows − 1) * grid_cols + (grid_cols − 1) = grid_cols * grid_rows − 1`. The super-goal ID is therefore one past the last real cell and never collides across any grid resize within the configured safe range. **Point ID encoding (binding convention):** AStar2D point IDs follow row-major order: `point_id = cell.y * grid_cols + cell.x` (equivalently: `row * grid_cols + col`). This convention must be applied consistently for all `add_point()` calls and the point_id → Vector2i lookup dictionary. The SUPER_GOAL_ID collision-safety proof depends on this ordering — any deviation (e.g., column-major, 1-indexed) invalidates the safety guarantee and may cause silent pathfinding graph corruption.
   - **Heuristic admissibility:** Subclass `AStar2D` and override `_estimate_cost(from_id, to_id)`. When `to_id == super_goal_id`, return `min(manhattan(cell_at(from_id), g) for g in goal_cells)`. This is admissible: the minimum Manhattan distance to any GOAL cell never exceeds the actual path cost to the nearest reachable GOAL. For all other `to_id` values, use the standard Manhattan formula (F1).
   - **`_compute_cost()` override (mandatory — zero-cost super-goal edges):** The subclass MUST also override `_compute_cost(from_id, to_id)` returning `0.0` when `to_id == super_goal_id`. Godot computes actual edge traversal cost via `_compute_cost()` using `distance × (from_weight_scale + to_weight_scale) / 2`. Without this override, the GOAL→super-goal edge cost equals `euclidean_distance(goal_position, Vector2.ZERO) × 0.5` — which is nonzero for any GOAL cell not at pixel (0,0). This biases A* toward GOAL cells nearest the grid origin in pixel space, silently breaking the "nearest reachable GOAL" semantic and causing AC-10 failures on real maps. Overriding only `_estimate_cost()` is not sufficient. See F1 `_compute_cost` note.
   - **Super-goal ID re-computation (binding):** `super_goal_id` must be re-computed at the start of every template build by reading `grid_cols` and `grid_rows` from the Grid (`Grid.get_grid_cols()` / `Grid.get_grid_rows()`). Do NOT cache these values as Autoload member variables across missions. On a small-to-large grid resize (e.g., G1=16×12 to G2=24×18), a stale `super_goal_id = 192` collides with valid G2 cell (col=0, row=8), silently corrupting the A* graph for the new mission.
   - **Stored path GOAL inclusion:** The stored `template.path` includes the GOAL cell as its final entry. The super-goal node (ID = `grid_cols * grid_rows`) is the only point stripped before storage. An empty returned path means no path exists — not "already at GOAL."

**IV. Pre-Placement Path Guard**

9. The Pathfinding System exposes: `would_block_all_paths(cells: Array[Vector2i]) -> bool`. It returns `true` if any SPAWN cell would have no path to any GOAL after marking `cells` as non-walkable. The procedure is:
   1. Call `Grid.get_walkable_cell_map().duplicate(true)` — deep copy of the current committed walkability map.
   2. Mark all cells in `cells` as non-walkable in the copy.
   3. Re-compute `temp_super_goal_id = Grid.get_grid_cols() * Grid.get_grid_rows()` from current grid dimensions — do not read from the instance variable (which may be stale if grid dimensions changed since last build).
   4. Populate `temp_goal_cells = Grid.get_goal_cells()`. This step is **mandatory** — the temporary AStar2D subclass instance's `goal_cells` member must be set before any A* query. Without it, `_estimate_cost()` returns `INF` with `push_error()` for every `to_id == temp_super_goal_id` evaluation (see AC-22, EC-12).
   5. Build a standalone temporary `PathfindingAStar2D` instance from the walkability copy: add all walkable cells with correct `weight_scale` values (Rule 17), add the super-goal node (ID = `temp_super_goal_id`, position = `Vector2.ZERO`, weight_scale = 0.0), connect each GOAL cell to the super-goal with a one-directional edge (GOAL → super-goal), set `astar.goal_cells = temp_goal_cells`.
   6. Run A* from each SPAWN cell to `temp_super_goal_id`. If any SPAWN cell produces an empty path, return `true`. If all SPAWNs have paths, return `false`.
   This function does not mutate the cached per-SPAWN instances.
   **Partial GOAL isolation (design decision):** If placing `cells` makes one GOAL unreachable but other GOALs remain reachable from all SPAWN cells, `would_block_all_paths()` returns `false` — placement proceeds. The affected SPAWN templates are marked dirty and rebuilt via the standard deferred path; `path_invalidated` fires and consumers update their route displays. No additional event is emitted for the GOAL isolation itself. This is the intended behavior: the game's chokepoint design assumes players can selectively cut off individual GOAL cells, and route-preview updates via `path_invalidated` communicate the resulting re-routing.
   **Precondition:** The caller guarantees all cells in `cells` are PLACEABLE cell type. Behavior is undefined if `cells` contains GOAL, PATH, or SPAWN cells — the Tower System must validate footprint cell types before calling this function.
   **Post-condition:** The `Grid.get_walkable_cell_map()` live state is unchanged after this call. The `.duplicate(true)` deep copy is mandatory — mutating the live Grid state would corrupt all subsequent walkability reads for the current frame. See AC-18.
10. The Tower System calls `would_block_all_paths(footprint)` **before** calling `Grid.place_tower`. This call fires only on **placement confirmation (click/release) — not on hover.** If it returns `true`, the Tower System rejects the placement and never writes to the Grid. No `path_invalidated` event is emitted. The Pathfinding System emits `tower_placement_blocked(blocked_cells: Array[Vector2i], primary_blocking_cell: Vector2i)` via EventBus within the same frame.
   - `blocked_cells`: the full footprint array (all cells that were submitted) — gives Mission HUD the complete rejected footprint for uniform highlight.
   - `primary_blocking_cell`: a single cell within `blocked_cells` that is individually load-bearing (i.e., `would_block_all_paths([primary_blocking_cell])` returns `true`). Computed by iterating `cells` in order and returning the first cell that passes an individual check. If no single cell in isolation causes the block (multi-cell interaction disconnection — the cells together close the lane but neither alone does), `primary_blocking_cell` is set to `Vector2i(-1, -1)` — a sentinel indicating "no single load-bearing cell." **Mission HUD contract:** if `primary_blocking_cell == Vector2i(-1, -1)`, highlight all `blocked_cells` uniformly (the footprint as a whole is the constraint — do not imply a single cell is load-bearing); if `primary_blocking_cell` is a valid grid cell, highlight it distinctively to anchor player attention to the specific constraint cell. This distinction prevents the player from building a false mental model of the map's spatial constraints — a pillar-critical requirement for "Placement is the Puzzle" legibility.
   - **Performance note:** `primary_blocking_cell` computation adds at most `footprint.size()` extra individual `would_block_all_paths()` calls, only on rejection frames (player-triggered). **MVP maximum tower footprint is 2×2 = 4 cells** (Tower GDD `foundation.footprint` = `Vector2i(1,1)` or `Vector2i(2,2)`). Worst-case rejection frame = (1 initial check + 4 individual checks) × per-call cost. If per-call cost ≤ 2ms, total ≤ 10ms — acceptable. If per-call cost > 2ms, add early-exit optimization (exit as soon as the first individually load-bearing cell is found — the contract only requires the first such cell). This constraint must be validated at Sprint 2 gate alongside AC-17. See AC-17 full rejection-frame budget note.
   - **EventBus dependency:** `tower_placement_blocked` payload (two fields: `blocked_cells`, `primary_blocking_cell`) confirmed in the EventBus GDD catalogue (verified review #5). ✅

**V. Template Invalidation and Rebuild**

11. Pathfinding subscribes to `tower_placed` and `tower_removed` from the Tower System. **WAVE_ACTIVE phase guard (mandatory):** The `tower_placed` and `tower_removed` handlers must include an explicit phase check at entry: `if current_phase == "WAVE_ACTIVE": push_error("PathfindingSystem: tower_placed/tower_removed received during WAVE_ACTIVE — Grid lock failure detected. Setting _tower_destroyed_during_wave = true to trigger INTERMISSION recovery rebuild."); _tower_destroyed_during_wave = true; return`. This is defense in depth — the Grid lock (Tower GDD Rule 8) is the primary enforcement mechanism, but Pathfinding must not silently corrupt templates if the lock fails. `push_error()` (not `push_warning()`) ensures this invariant violation is visible in error logs and CI failure output. Setting `_tower_destroyed_during_wave = true` ensures the INTERMISSION entry handler marks all templates dirty and queues a recovery rebuild — the same path used for BOSS tower destruction. Without this flag, a Grid-lock failure that writes to the Grid during WAVE_ACTIVE causes permanent template divergence with no recovery. See AC-23. On receipt with a valid phase, it checks each template's `cell_index_map` for any cell in the event's footprint. Templates containing any footprint cell are marked dirty. **`_dirty_templates` structure:** `Dictionary[Vector2i, bool]` mapping SPAWN cell coordinate → dirty flag. `_dirty_templates[spawn_cell] = true` marks that SPAWN's template for rebuild. Only SPAWN cells whose template's `cell_index_map` contains at least one footprint cell are marked. At MVP with a single SPAWN, at most one entry ever exists. `_dirty_templates` is cleared to `{}` after all dirty templates are rebuilt (see Rule 14). On mission restart or phase exit to OUTCOME/DEFEAT, `_dirty_templates` is also cleared immediately — any in-flight deferred rebuild is abandoned without emitting `path_invalidated`.
   **Canonical key type note:** `Dictionary[Vector2i, bool]` keying by SPAWN cell coordinate is canonical and consistent with `_spawn_assignment`'s value type. The third review log (Blocker R7) recorded this as `Dictionary[int, bool]` — that entry reflects an in-session draft superseded during that same review.
   **BOSS tower-destruction tracking:** PathfindingSystem also subscribes to `tower_destroyed` via EventBus. During WAVE_ACTIVE, the Grid cell is freed but templates must not rebuild (Rule 20). On `tower_destroyed` receipt during WAVE_ACTIVE: set `_tower_destroyed_during_wave: bool = true`. On `mission_phase_changed(new_phase == "INTERMISSION")`: if `_tower_destroyed_during_wave` is `true`, mark ALL templates dirty in `_dirty_templates` and queue the deferred rebuild via the standard `_rebuild_queued` path (Rule 12). Clear `_tower_destroyed_during_wave = false`. This ensures BOSS-induced stale routing is corrected before the first monster of the next wave spawns, regardless of whether the player places or removes any towers in INTERMISSION.
   **Restart clear:** On mission restart or phase exit to OUTCOME/DEFEAT, `_dirty_templates` is cleared to `{}`, `_rebuild_queued` is explicitly cleared to `false`, and `_tower_destroyed_during_wave` is cleared to `false`. Any in-flight deferred rebuild is abandoned without emitting `path_invalidated`.
12. Dirty templates are rebuilt via `call_deferred` — executing at the **end of the current main loop iteration, before the next physics tick.** In Godot 4, `call_deferred` flushes after the current processing step completes: if `tower_placed` originates in `_physics_process()`, the rebuild fires after the physics step, before the next render frame; if it originates in `_process()`, it fires at the end of the render frame. In both cases the rebuild completes before the next `_physics_process()` tick, so all `get_path()` calls in the following physics frame see the updated templates. **WaveManager gate constraint:** The `is_rebuild_pending()` check at INTERMISSION→PRE_WAVE must be made from a `_physics_process()` callback (not `_process()`) to guarantee it reads `_rebuild_queued` state consistent with the most recent physics step. **Deduplication:** Godot 4.x `call_deferred` does NOT deduplicate — multiple calls in the same frame queue multiple executions. To guarantee exactly one rebuild and one `path_invalidated` emission per frame batch, the system uses a `_rebuild_queued: bool` flag. On receipt of any `tower_placed`/`tower_removed` event: mark `_dirty_templates` AND, if `_rebuild_queued` is `false`, set `_rebuild_queued = true` and call `call_deferred("_rebuild_dirty_templates")`. At the start of `_rebuild_dirty_templates`: **empty-dirty guard** — if `_dirty_templates` is empty (`{}`), clear `_rebuild_queued = false` and return immediately without emitting `path_invalidated` (prevents spurious emissions from stale deferred calls after mission restart). Then clear `_rebuild_queued = false` and proceed. Multiple events in the same frame accumulate into `_dirty_templates` but trigger only one deferred call. This guarantees AC-9a ("exactly one `path_invalidated` emitted" for N simultaneous tower events).
   **Intentional one-frame-stale routing window:** between a `tower_placed`/`tower_removed` event and `path_invalidated` emitting, any consumer that reads path state works with the pre-change route. During SCOUT and INTERMISSION (the only phases where tower events fire), no monsters are active, so this staleness window has no gameplay impact on monster routing.
   **Wave-start deferred-rebuild conflict (INTERMISSION → WAVE_ACTIVE):** The `templates_ready` event gates only the first `monster_spawn_requested`. For subsequent wave transitions, a deferred rebuild may still be queued when the WaveManager attempts to start the wave. **WaveManager gate:** PathfindingSystem exposes `is_rebuild_pending() -> bool`, which returns `true` if `_rebuild_queued` is currently `true`. WaveManager must call `PathfindingSystem.is_rebuild_pending()` **once** at the INTERMISSION→PRE_WAVE transition. If it returns `true`, WaveManager waits for `path_invalidated` before emitting `monster_spawn_requested`. If it returns `false`, WaveManager proceeds immediately. This replaces any reference to the internal `_rebuild_queued` state in cross-system contracts. See Dependencies section for the Wave Manager cross-GDD update.
13. Rebuild procedure (per dirty template):
    - **Entry guard (mandatory):** At the start of `_rebuild_dirty_templates()`, after the empty-dirty guard (Rule 12), check `if current_phase == "WAVE_ACTIVE": push_error("PathfindingSystem._rebuild_dirty_templates: called during WAVE_ACTIVE — deferred call survived a phase transition. Clearing rebuild state without emitting path_invalidated."); _rebuild_queued = false; _dirty_templates = {}; return`. A deferred call queued late in INTERMISSION may fire in the first WAVE_ACTIVE frame before Godot's deferred-call flush respects the phase boundary. This guard ensures templates are never silently modified mid-wave.
    - a. Re-read `grid_cols` and `grid_rows` from the Grid (`Grid.get_grid_cols()` / `Grid.get_grid_rows()`). Do NOT use any cached value — grids may resize between missions and stale dimensions invalidate the super-goal ID collision-safety proof (Rule 8).
    - b. Re-compute `super_goal_id = grid_cols * grid_rows` for this build. This step is **mandatory per build** — not once per session (see Rule 8 super-goal ID re-computation binding and Rule 21).
    - c. Call `Grid.get_walkable_cell_map()` for a fresh walkability snapshot.
    - d. Call `astar.clear()` on this SPAWN cell's AStar2D instance. **Important:** `clear()` resets the graph topology but does NOT reset subclass member variables — `goal_cells` becomes stale and must be explicitly repopulated in step (e). Any A* query run after `clear()` before step (e) completes will use stale `goal_cells`, causing the `_estimate_cost()` guard to fire `push_error()` and return `INF`.
    - e. Repopulate `goal_cells` from `Grid.get_goal_cells()`. This step is **mandatory after every `clear()`** — `clear()` does not reset subclass member variables. On mission restart, the prior mission's GOAL cells remain in memory until overwritten here. Without this step, `_estimate_cost()` operates on the previous mission's GOAL positions.
    - f. Repopulate the AStar2D graph: add all walkable cells with correct `weight_scale` values (Rule 17), add the super-goal node (point ID = `super_goal_id`, position = `Vector2.ZERO`, weight_scale = 0.0), connect each GOAL cell to the super-goal with a **one-directional edge** (GOAL → super-goal only — do not add the reverse super-goal → GOAL edge, which would allow A* to route monsters through the virtual node as a waypoint).
    - g. Run A* from the SPAWN cell to `super_goal_id`. Convert the returned `PackedInt64Array` to `Array[Vector2i]` via the `point_id → Vector2i` lookup dictionary. Strip the super-goal node from the result. The stored path includes the GOAL cell as its final entry.
    - h. Rebuild `cell_index_map` from the new path. Store the updated template.
14. After all dirty templates are rebuilt, emit `path_invalidated` (EventBus): `affected_cells: Array[Vector2i]` = union of all footprint cells from all tower events batched this frame.

**VI. `get_path()` API**

15. `get_path(from_cell: Vector2i, tier: int) -> Array[Vector2i]` (returns `[]` or a non-empty `Array[Vector2i]`):
    - **Threading constraint:** `get_path()` is not thread-safe and must only be called from the **main thread** — including from `_process()`, `_physics_process()`, or deferred calls. Calling `get_path()` from any `Thread` or `WorkerThreadPool` task is **forbidden**. The fallback path (Rule 15e) mutates an `AStar2D` instance without a mutex; concurrent off-thread calls corrupt the graph and produce silent pathfinding errors with no crash or assert. Note: in Godot 4 GDScript, `_physics_process()` is always dispatched from the main thread — the threading risk comes from explicit `WorkerThreadPool.add_task()` or `Thread` usage (e.g., pre-computing paths for upcoming wave monsters during INTERMISSION), not from standard `_physics_process()` callbacks.
    - a. **Pre-init guard**: if `_templates_built == false`, call `push_error("PathfindingSystem.get_path: called before templates_ready — returning []")` and return `[]` immediately. This prevents a pre-initialization race (where `_spawn_assignment` is empty and fallback A* would silently return `[]` — indistinguishable from GOAL arrival) from propagating to consumers.
    - b. **Tier guard**: at MVP, all tiers use identical routing. If `tier != STANDARD`, call `push_warning("get_path: tier parameter reserved for MVP")`. Proceed with standard routing regardless.
    - c. **Template lookup**: look up `_spawn_assignment[from_cell]` to select the relevant template. If `from_cell` is absent from `_spawn_assignment` (template initialization failure), call `push_error("PathfindingSystem.get_path: from_cell %s not in _spawn_assignment — possible initialization failure" % str(from_cell))` and fall through to fallback A*. If the returned SPAWN key has no corresponding entry in the template dictionary (partial initialization failure — SPAWN assigned but template not built), call `push_error("PathfindingSystem.get_path: SPAWN %s has no template — partial initialization failure" % str(spawn_key))` and fall through to fallback A*.
    - d. **Slice**: look up `from_cell` in the template's `cell_index_map`. If `from_cell in template.cell_index_map` is true, compute the slice using the type-safe pattern from F3: `var result: Array[Vector2i] = []; result.assign(template.path.slice(template.cell_index_map[from_cell] + 1)); return result`. Do NOT use `return template.path.slice(...)` directly — `.slice()` on a typed `Array[Vector2i]` returns an untyped `Array` in GDScript 4, violating the mandatory static-typing standard (F3 binding note). A `[]` result means `from_cell` is the GOAL cell — Monster System treats this as arrival. Complexity: O(1) dictionary lookup + O(k) array copy where k = remaining path length. Known hotspot: 100 monsters × average k=25 = 2500 cell copies per frame. See OQ-6 for performance validation requirements before committing to this hot path.
    - e. **Fallback**: if `from_cell` is not in the assigned template's `cell_index_map` (monster drifted off-path after invalidation), attempt a standalone temporary `AStar2D` built from `Grid.get_walkable_cell_map().duplicate(true)` with the same super-goal trick (Rule 8). **Before running A\***, populate the subclass instance's `goal_cells` member from `Grid.get_goal_cells()` — this initialization step is mandatory; `_estimate_cost` returns `INF` with `push_error()` if `goal_cells` is empty (see AC-22b). Then run A* from `from_cell` to the super-goal. Set `last_fallback_warning: String` to the warning message (e.g., `"PathfindingSystem.get_path: fallback A* fired for cell %s — possible level design issue or off-template drift" % str(from_cell)`) — this public field is reset to `""` at the start of each `_physics_process()` and allows tests to assert whether the fallback fired (see AC-11). Also call `push_warning(last_fallback_warning)`. Return the result path (GOAL cell included, super-goal stripped) or `[]` if unreachable. Do not cache this result.
      **Fallback cap:** A `_fallback_count_this_frame: int` counter tracks fallbacks this frame. **Check order (binding):** the cap check fires BEFORE incrementing and BEFORE running A* — if `_fallback_count_this_frame >= pathfinding_max_fallbacks_per_frame`, return `[]` immediately without touching the counter. Otherwise run A* and increment after completion. If `_fallback_count_this_frame >= pathfinding_max_fallbacks_per_frame` when a fallback is requested, the system returns `[]` instead of computing a path — the monster freezes movement this frame and retries next frame via its own re-query. There is no persistent cross-frame queue; each monster retries independently. At default cap of 1, N simultaneously-off-template monsters resolve over N frames.
      **Counter reset (binding):** `_fallback_count_this_frame` is reset to `0` at the start of PathfindingSystem's own `_physics_process()` callback, before any monster `_physics_process()` callbacks run. PathfindingSystem must be registered with a higher `process_priority` value (lower integer — runs earlier) than all Monster System nodes. This ordering is mandatory: if a monster's `_physics_process()` runs before PathfindingSystem's reset, the monster reads the prior frame's accumulated count, artificially exhausting the cap.
      **Two-value return contract:** `get_path()` returns exactly one of: `[]` (GOAL arrival, unreachable cell, or fallback cap exhausted — Monster System must stop movement this frame), or a non-empty `Array[Vector2i]` (valid remaining path). Monster System: check `if result.is_empty()` first, then treat non-empty result as valid path. A monster at the GOAL cell receives `[]` from the template slice (F3) and treats it as arrival. A monster whose fallback is capped also receives `[]` and retries next frame — it cannot distinguish GOAL arrival from cap-exhaustion without checking its own position against a GOAL cell (Monster System responsibility).

**VII. A* Parameters**

16. Movement: 4-directional (cardinal only). Diagonal moves are not permitted.
17. Cell costs: PATH = 1, SPAWN = 1, GOAL = 1, unoccupied PLACEABLE = 10. The elevated PLACEABLE cost biases routing toward designated PATH lanes; monsters only traverse PLACEABLE cells when no cardinal-PATH alternative exists.
18. Heuristic: Manhattan distance. Admissible for cardinal-only movement (never overestimates actual cost).
19. Implementation: Godot `AStar2D` (C++ backed — do not reimplement in GDScript). One `AStar2D` instance per SPAWN cell; cleared and repopulated on each dirty rebuild.

**19a. Point ID Encoding Convention (binding):** All `AStar2D.add_point()` calls must use row-major encoding: `point_id = cell.y * grid_cols + cell.x`. Inverse lookup: `cell.x = point_id % grid_cols`, `cell.y = point_id / grid_cols` (integer division). Worked example: at `grid_cols = 16`, cell (col=2, row=3) → `point_id = 3 × 16 + 2 = 50`. This rule applies to all `add_point()` calls and all `PackedInt64Array` → `Vector2i` lookups (Rules 13c, 15d, 8). **Warning:** column-major encoding (`point_id = cell.x * grid_rows + cell.y`) produces a graph that compiles and runs with no crash or warning while routing all monsters along transposed grid coordinates. Any deviation from row-major also invalidates the SUPER_GOAL_ID collision-safety proof in Rule 8.

**VIII. Phase Behavior**

20. Tower writes are locked by the Grid during `WAVE_ACTIVE`. Therefore, `path_invalidated` is only ever emitted during SCOUT and INTERMISSION — not during active waves. During WAVE_ACTIVE, all templates are stable; active monsters hold valid local path copies.
21. On mission restart (DEFEAT → SCOUT): all templates are cleared; `_templates_built` is reset to `false`; `_spawn_assignment` is cleared to `{}`; `_dirty_templates` is cleared to `{}`; `_rebuild_queued` is reset to `false`; `_tower_destroyed_during_wave` is reset to `false`. Any locally cached `grid_cols`, `grid_rows`, or `super_goal_id` values from the prior mission must not be used — they will be re-read from the Grid at the start of the next template build (Rule 13a–b). Templates are rebuilt from the fresh `GridConfig` when `mission_phase_changed(new_phase == "SCOUT")` fires for the new mission.

### Level Design Authoring Guidelines

These constraints apply to any mission map whose GridConfig is consumed by the Pathfinding System. Violating them does not crash the engine but produces silent routing failure or degenerate gameplay.

**Mandatory constraints (CI-enforced via AC-13/13b/13c/13d):**
- The mission must contain ≥1 SPAWN cell and ≥1 GOAL cell. Maps with zero SPAWN or GOAL cells fail AC-13 validation.
- Every SPAWN cell must have a connected A* path to at least one GOAL cell on the initial grid (all PLACEABLE cells unoccupied). Maps with no initial route fail AC-13c validation.
- At MVP, the mission must contain exactly one SPAWN cell. Multi-SPAWN missions fail AC-13d validation.
- No critical lane may be 1 cell wide. A **critical lane** is any PATH corridor that is the sole connection between any SPAWN-reachable map region and a GOAL cell. A 1-cell-wide critical lane means the first tower placed there triggers `would_block_all_paths() == true` — the puzzle is unsolvable from that point. CI validates this via AC-13b solo-block checks.
- No 2×2 PLACEABLE group adjacent to a PATH corridor may constitute the sole route connection — this would mean a standard 2×2 tower permanently closes the path. AC-13b catches this with the 2×2 footprint check.

**Design guidance (not CI-enforced — author responsibility):**
- Minimum SPAWN-to-GOAL Manhattan distance: ≥8 cells. Shorter maps give monsters too little time on-screen for tower interactions to be meaningful.
- PATH corridor minimum width for any lane the player is expected to use as a chokepoint: 2 cells. 3 cells is recommended for lanes intended to support multiple simultaneous tower types.
- PLACEABLE cells adjacent to both sides of a critical PATH lane allow double-stacking towers — this is a legitimate design choice but removes the player's ability to form a choke and should be intentional, not accidental.
- Keep SPAWN and GOAL cells away from the map edge where possible — SPAWN cells at corner positions limit approach angles and constrain future multi-SPAWN expansion.
- Test each mission map with the CI validator (`tools/validate_mission_map.gd`) before committing to version control. The validator catches all constraint violations listed above and provides descriptive error output per failing cell.

## Formulas

#### F1 — Manhattan Distance Heuristic

| Variable | Type | Description |
|----------|------|-------------|
| `current` | Vector2i | Cell currently being evaluated in A* |
| `goal` | Vector2i | Target GOAL cell (or super-goal equivalent) |
| `h` | int | Estimated cost to goal |

**Expression:**
```
h(current, goal) = abs(goal.x - current.x) + abs(goal.y - current.y)
```

Admissible for 4-directional movement on a grid where minimum step cost = 1. Never overestimates the true path cost, guaranteeing A* finds the optimal path.

**Output range:** 0 (current = goal) to `(grid_cols - 1) + (grid_rows - 1)` — 26 at the default 16×12 grid (opposite corners), 40 at the maximum 24×18 grid.

**Super-goal heuristic override (piecewise):** Rule 8's `_estimate_cost` override adds a second branch to this formula:
```
_estimate_cost(from_id, to_id):
  if to_id == super_goal_id:
    if goal_cells.is_empty():
      push_error("PathfindingSystem._estimate_cost: goal_cells is empty — returning INF. goal_cells must be initialized before any A* query on this AStar2D subclass instance.")
      return INF
    return min(manhattan(cell_at(from_id), g) for g in goal_cells)
  else:
    if from_id == super_goal_id:
      return 0.0  # super-goal is the search endpoint; no real cell to compute distance from
    return abs(cell_at(to_id).x - cell_at(from_id).x) + abs(cell_at(to_id).y - cell_at(from_id).y)  # standard F1
```
Both branches are admissible: minimum Manhattan to any GOAL never exceeds actual path cost to nearest reachable GOAL when all step costs ≥ 1 (PATH/SPAWN/GOAL = 1, PLACEABLE = 10 ≥ 1).

**`_compute_cost()` override (mandatory — actual edge traversal cost):** Rule 8 mandates overriding `_compute_cost(from_id, to_id)` to enforce zero-cost GOAL→super-goal edges. Without this override, Godot's default implementation computes `euclidean_distance(goal_position, super_goal_position) × (goal_weight_scale + 0.0) / 2` — nonzero for any GOAL cell not at pixel `(0, 0)`, silently biasing A* toward GOAL cells near the grid origin.

**Coordinate space (binding):** The `from_id` and `to_id` parameters received by `_compute_cost` are the AStar2D point IDs assigned during `add_point()` calls — they are row-major cell indices (`point_id = cell.y * grid_cols + cell.x`, per Rule 8 and Rule 19a). To recover a Vector2i from a point ID inside `_compute_cost`: `cell.x = point_id % grid_cols`, `cell.y = point_id / grid_cols` (integer division). The `position_at(id)` pseudocode below retrieves the Vector2 registered at `add_point()` — this requires a `point_id → Vector2` lookup dictionary maintained alongside the AStar2D instance. Do not call `AStar2D.get_point_position(id)` as an alternative — Godot 4 does not guarantee this API is stable across all 4.x versions; use the local lookup dict.

```
_compute_cost(from_id, to_id):
  if to_id == super_goal_id:
    return 0.0  # Zero-cost virtual edge — super-goal has no real grid position
  if from_id == super_goal_id:
    push_error("PathfindingSystem._compute_cost: from_id == super_goal_id — super-goal should never be a traversal source. Returning 0.0.")
    return 0.0
  # from_id and to_id are row-major cell indices; position_at() reads the local point_id→Vector2 dict
  return position_at(from_id).distance_to(position_at(to_id)) * (weight_scale_at(from_id) + weight_scale_at(to_id)) / 2.0
```
The `from_id == super_goal_id` branch should never fire in a correctly wired graph (the super-goal is a search sink, not a source). The `push_error()` there surfaces any graph wiring mistake during development. This override is required on all PathfindingAStar2D subclass instances — both the per-SPAWN template instances and the temporary instances in `would_block_all_paths()` and Rule 15e.

**`goal_cells` initialization requirement (binding):** Every instance of this AStar2D subclass — both the per-SPAWN template instances built during Rule 5 and the standalone temporary instance built inside `would_block_all_paths()` — must have its `goal_cells` member populated from `Grid.get_goal_cells()` before any A* query runs. Without this, the `is_empty()` guard fires and returns `INF`, which is safe but emits a `push_error()`. Failing to provide `goal_cells` to the temporary graph inside `would_block_all_paths()` is the primary risk path: the temporary instance is constructed ad-hoc and its initialization is not protected by the Rule 5 precondition. See AC-22.

#### F2 — Cell-to-SPAWN Assignment (Voronoi Partition)

| Variable | Type | Description |
|----------|------|-------------|
| `cell` | Vector2i | Any walkable cell in the grid |
| `spawn_cells` | Array[Vector2i] | All SPAWN cells from `Grid.get_spawn_cells()` |
| `assigned_spawn` | Vector2i | The SPAWN cell coordinate this cell is assigned to |

**Expression:**
```
# Precondition: spawn_cells.size() >= 1 (enforced by Rule 5 precondition — hard error if empty)
var nearest_idx := 0
for i in range(spawn_cells.size()):
    if chebyshev(cell, spawn_cells[i]) < chebyshev(cell, spawn_cells[nearest_idx]):
        nearest_idx = i
assigned_spawn_cell = spawn_cells[nearest_idx]  # Vector2i coordinate — not an array index

chebyshev(a, b) = max(abs(a.x - b.x), abs(a.y - b.y))
```

Computed once at SCOUT start for all walkable cells. Results stored in `_spawn_assignment: Dictionary[Vector2i, Vector2i]` — each key is a walkable cell, each value is the nearest SPAWN cell coordinate (used directly as the template dictionary key). Used by `get_path(from_cell)` for O(1) template selection via `_spawn_assignment[from_cell]`. Ties broken by lower array index (first SPAWN in `get_spawn_cells()` order) — deterministic but ordering-dependent; **at MVP (N=1, CI-enforced — see Tuning Knobs' Mandatory constraints and AC-13d) ties never occur.** *(Corrected 2026-07-15d — an earlier same-day pass mistakenly rewrote this note to claim multi-SPAWN maps are ordinary MVP content, based on wave-manager.md's AC-10 test fixture. That was backwards: AC-13d is a deliberate, CI-enforced gate — this algorithm's Chebyshev-distance tie-break is documented [see the `_compute_spawn_assignment()` code-spec TODO, Rule 1] as producing incorrect assignment for cells near walls between SPAWNs, so multi-SPAWN maps are explicitly blocked from shipping until the reverse-Dijkstra replacement lands post-MVP. wave-manager.md's AC-10 fixture was the actually-wrong document and has been corrected there instead — see its own revision note.)*

**Note:** Keying by SPAWN cell coordinate (not array index) makes `_spawn_assignment` and `_dirty_templates` independent of `get_spawn_cells()` return order — no ordering contract is required of the Grid.

**Output range:** a SPAWN cell coordinate (Vector2i) from `Grid.get_spawn_cells()`. At MVP, N = 1, so all assignments equal the single SPAWN cell coordinate.

**Population scope:** `_spawn_assignment` is populated for ALL walkable cells, explicitly including SPAWN cells and GOAL cells (both have `weight_scale = 1.0` in the AStar2D graph and are walkable). A monster calling `get_path()` from a SPAWN cell at spawn, or from a GOAL cell on arrival, must find its cell in `_spawn_assignment`. "All walkable cells" = all cells added to the AStar2D graph (PATH, SPAWN, GOAL, and unoccupied PLACEABLE cells).

#### F3 — Template Path Slice

| Variable | Type | Description |
|----------|------|-------------|
| `template.path` | Array[Vector2i] | Full cached route from SPAWN to GOAL |
| `template.cell_index_map` | Dictionary[Vector2i, int] | Reverse lookup: cell → index in path |
| `from_cell` | Vector2i | Monster's current grid cell |
| `result` | Array[Vector2i] | Remaining path from from_cell to GOAL |

**Expression:**
```
# Guard: call only when from_cell in template.cell_index_map (Rule 15d handles fallback)
idx = template.cell_index_map[from_cell]   # 0-based index of from_cell in path
var result: Array[Vector2i] = []
result.assign(template.path.slice(idx + 1))  # excludes from_cell; returns [] at GOAL cell
```
**Type annotation note (binding):** In GDScript 4, `.slice()` on a typed `Array[Vector2i]` returns an untyped `Array` — the type annotation is silently dropped. Assigning directly via `result.assign(...)` where `result: Array[Vector2i]` preserves the type annotation and satisfies the mandatory static-typing standard. Do NOT write `var result = template.path.slice(idx + 1)` (infers untyped `Array`) or `var result: Array[Vector2i] = template.path.slice(idx + 1)` (compiles but may strip the type at runtime depending on Godot version — verify against Godot 4.6 changelog before using this form).

**Complexity:** O(1) lookup + O(k) slice where k = remaining path length. No re-computation during WAVE_ACTIVE.

**Output range:** 0 cells when `from_cell` is the GOAL cell (`slice(len)` past end of array = `[]`) to `template.path.size() − 1` cells when at the SPAWN cell. Result excludes `from_cell` itself. **At GOAL cell:** result is `[]` — Monster System must treat an empty return as arrival and stop querying. **Guard required:** `from_cell` must be a key in `template.cell_index_map`. If not present, use the fallback A* path (Rule 15d).

**Variant overhead note:** `Array[Vector2i]` in GDScript stores each element as a Variant (~28 bytes each, vs 8 bytes for a packed struct). 100 monsters × average 25 cells × ~28 bytes ≈ 70 KB of Variant allocations per frame, with associated GC pressure beyond raw copy cost. The 1ms figure in AC-4 is a working hypothesis. Cross-reference: Monster System AC-28 budgets 2ms total for all Monster System `_physics_process` work — the `get_path()` sub-budget must be explicitly allocated within that 2ms. See OQ-6 for the validation gate.

#### F4 — PLACEABLE Cell Cost Ratio Justification

| Variable | Type | Value | Description |
|----------|------|-------|-------------|
| `cost_path` | int | 1 | Step cost for PATH, SPAWN, GOAL cells |
| `cost_placeable` | int | 10 | Step cost for unoccupied PLACEABLE cells |
| `ratio` | int | 10 | PLACEABLE / PATH cost ratio |

**Cost model note (binding):** Godot's `AStar2D` uses an averaging formula for edge costs: `edge_cost = distance × (from_weight_scale + to_weight_scale) / 2`. With PATH `weight_scale = 1` and PLACEABLE `weight_scale = W`, the actual per-edge costs are:
- PATH→PLACEABLE: `(1 + W) / 2`
- PLACEABLE→PLACEABLE: `W`
- PLACEABLE→PATH: `(1 + W) / 2`
- Full PATH→PLACEABLE→PATH crossing (enter + exit): `1 + W`

This averaging is a Godot 4 engine behavior applied automatically to every `AStar2D.add_point(weight_scale)` call. Rule 17's `weight_scale` values are unchanged; only the crossing-cost analysis below is corrected to reflect averaging.

**Interpretation and practically relevant threshold:** A monster crossing P consecutive PLACEABLE cells incurs cost `W×P + 1` (one entry/exit boundary effect of total cost `1 + W`, plus `(P−1)×W` for internal PLACEABLE→PLACEABLE traversal). The monster prefers crossing when `W×P + 1 < D` (D = PATH detour cost in steps at 1 per step). **The practically relevant case is P=1 (a single PLACEABLE cell):** monsters cross one PLACEABLE cell whenever the PATH detour exceeds `W + 1` steps. At default W=10: detour > 11 steps. On a 16×12 grid, 11-step detours occur in well-designed mazes — level designers should expect monsters to occasionally cut a single PLACEABLE cell when the PATH lane adds more than 11 steps. For P PLACEABLE cells: threshold is `D > W×P + 1` (e.g., at W=10: 2 cells: detour > 21 steps; 5 cells: detour > 51 steps).

**Design bound:** At W=2: full crossing costs 3, monsters cross at any PATH detour > 3 steps — casual cutting, placement decisions lose legibility. At W=6: full crossing costs 7, monsters cross at detour > 7 steps — 7-step detours require meaningful maze structure on a 16×12 grid, preserving placement legibility. **Safe range minimum is W=6.** W > 20: crossing costs > 21, requiring a detour spanning the full 16-cell grid width to trigger 1-cell cuts — may cause pathfinding failures on constrained maps.

## Edge Cases

**EC-1: Monster spawns at the SPAWN cell**
The assigned SPAWN cell's template is used. `cell_index_map[spawn_cell]` returns index 0, so `get_path()` returns `template.path.slice(1)` — the route from the first step after SPAWN to GOAL, with the SPAWN cell itself excluded (Rule 15d, F3). No fallback needed for standard spawns. **Exception — no-path map (EC-7):** if `template.path == []`, `spawn_cell` is absent from `cell_index_map` (the template was built with no valid route). Rule 15c fires: `_spawn_assignment` miss → fallback A* from `spawn_cell`. If the route is still blocked, fallback returns `[]` — Monster System stops the monster at spawn. **Exception — degenerate SPAWN==GOAL map:** `slice(1)` on a 1-entry path `[spawn_cell]` returns `[]` — Monster System treats as immediate GOAL arrival. Both are content-authoring errors, not runtime bugs; AC-13c and the Rule 5 precondition guard are the prevention layers.

**EC-2: Monster's current cell not found in rebuilt template after invalidation**
After a template rebuild, a monster at cell (7,4) calls `get_path(Vector2i(7,4), tier)`. If cell (7,4) is no longer in the new template (rebuild routed differently), the fallback A* from (7,4) fires, logs a warning, and returns a fresh path. This is a valid case — monster is mid-grid after a route change.

**EC-3: All routes blocked by tower placement — prevented by guard**
`would_block_all_paths(footprint)` returns `true`. Tower System rejects the placement. The Grid is never written. No templates are dirtied. No `path_invalidated` is emitted. The player's placement cursor shows a blocked indicator. This is the normal prevention path, not an error state.

**EC-4: `get_path()` called during WAVE_ACTIVE (normal operation)**
Templates are stable during WAVE_ACTIVE (no tower writes possible). All calls return valid slices from cached templates. No A* computation occurs. This is the primary hot path.

**EC-5: Mission has exactly one SPAWN cell**
One template is computed. No Voronoi partition needed — all walkable cells assign to the single SPAWN. Super-goal logic still applies if multiple GOAL cells exist.

**EC-6: Mission has exactly one GOAL cell**
The super-goal node is still added for architectural consistency, but has no multi-GOAL effect. A* terminates at that single cell regardless. No special-casing needed.

**EC-7: Template build before any tower is placed (mission start)**
All PLACEABLE cells are unoccupied (cost 10). If the mission's PATH layout provides a complete route from SPAWN to GOAL, templates compute normally. If the PATH layout alone provides no complete route (malformed mission map), templates store `[]`. This is a content-authoring error, not a runtime error.

**EC-8: Tower removed during INTERMISSION restores a previously blocked cell**
`tower_removed` fires. Dirty templates are rebuilt. The new A* may find a shorter path through the now-unblocked cells. `path_invalidated` is emitted. Monsters spawning in the next wave receive the shorter path.

**EC-9: `AStar2D.get_id_path()` returns `PackedInt64Array`**
The point_id-to-Vector2i lookup dictionary handles the conversion. The super-goal node's point_id must be excluded from the dictionary and filtered from the returned path before template storage.

**EC-10: Two SPAWN cells equidistant from a walkable cell (Voronoi tie)**
Both SPAWN cells have equal Chebyshev distance. Tie-break: first SPAWN in `get_spawn_cells()` array order. Deterministic and stable.

**EC-11: Tower destroyed during WAVE_ACTIVE (any source)**
Any game system that reduces a tower's HP to 0 fires `tower_destroyed` (BOSS attacks, environmental hazards, or future mechanics). The `tower_destroyed` handler in PathfindingSystem responds to all sources — no BOSS-ID filter is applied. At MVP, only BOSS attacks can destroy towers; this rule ensures the handler is not inadvertently written to filter by source, which would break auto-rebuild when non-BOSS destruction is added. Grid frees the cell. Pathfinding receives the event but does NOT rebuild templates during WAVE_ACTIVE — template stability is mandatory during active waves (Rule 20). Monsters continue to route around the empty cell for the remainder of the wave.
**Automatic correction at INTERMISSION entry:** PathfindingSystem subscribes to `tower_destroyed` and sets `_tower_destroyed_during_wave = true` on receipt during WAVE_ACTIVE. When `mission_phase_changed(new_phase == "INTERMISSION")` fires, the system marks all templates dirty and queues a deferred rebuild via the standard `_rebuild_queued` path (Rule 11 BOSS tracking, Rule 12). This rebuild completes before the next wave starts, regardless of whether the player places or removes any towers in INTERMISSION. Monsters spawning in the next wave receive the corrected template.
**Stale route duration:** During the wave in which the BOSS destroys the tower, routing remains stale (intentional — mid-wave rebuilds are not allowed). The stale behavior is automatically corrected at INTERMISSION entry. Templates do NOT persist incorrectly across waves.
**Player legibility:** Monsters visibly routing around an empty cell for the remainder of the current wave is a visible but time-limited side effect of BOSS combat. **Mission HUD responsibility:** The Mission HUD must subscribe to `tower_destroyed` during WAVE_ACTIVE and display a player-visible communication such as "Path update queued for next intermission." The specific presentation (banner, pop-over, audio cue) is delegated to Mission HUD authoring.

**EC-12: Phantom GOAL arrival from empty `goal_cells` in Rule 15e fallback**
If the Rule 15e temporary AStar2D subclass is constructed without populating `goal_cells` (initialization step omitted), `_estimate_cost()` fires `push_error()` and returns `INF` for every `to_id == super_goal_id` evaluation. A* finds no path and returns an empty `PackedInt64Array`, which `get_path()` converts to `[]`. The Monster System treats `[]` as GOAL arrival and stops the monster at its current off-template position. **Result:** the monster freezes mid-map with no further movement, effectively bypassing all remaining towers and dealing no further Sanctuary damage — a silent outcome with no player-visible or error-visible signal beyond the `push_error()` in `_estimate_cost()`. **Prevention:** Rule 15e's fallback construction step explicitly includes `goal_cells` population from `Grid.get_goal_cells()` (Rule 15e binding text, step before running A*). AC-22b validates this initialization path. This edge case cannot occur if Rule 15e is implemented correctly.

## Tuning Knobs

| Knob | Owner | Default | Safe Range | Gameplay Effect |
|------|-------|---------|-----------|-----------------|
| `pathfinding_placeable_cost` | Pathfinding (this GDD) | 10 | 6–20 | `weight_scale` for unoccupied PLACEABLE cells. Due to Godot's `AStar2D` averaging formula (F4 cost model note), a full PATH→PLACEABLE→PATH crossing costs `W + 1` — monsters cross 1 PLACEABLE cell when PATH detour > `W + 1` steps. Below 6 (detour threshold < 7 steps): monsters cut on any 7-step detour — placement legibility degrades. Above 20 (threshold > 21 steps): requires a detour spanning the full 16-cell grid width to trigger cutting — may cause pathfinding failures on constrained maps. **Level design constraint:** PATH corridors must be ≥2 cells wide in any **critical lane** (defined as any PATH corridor that is the sole connection between any SPAWN-reachable map region and a GOAL cell). A 1-cell-wide critical lane means any tower placed there triggers `would_block_all_paths()` — the puzzle becomes unsolvable before the player has a strategic choice. This constraint must be enforced during mission map authoring and CI validation (AC-13b, AC-13c). **Minimum detour length at W_min=6:** At W=6, a full crossing costs 7, so monsters cut a single PLACEABLE cell at PATH detours > 7 steps. Mission authors must ensure critical lane bypass detours are ≥8 PATH steps at W=6 to prevent unintended routing shortcuts. **Constrained maps (W > 20):** Raising the cost above 20 requires a PATH detour spanning the full 16-cell grid width (> 21 steps) to trigger any cutting. On dense maps where the longest possible detour is < 21 steps, monsters never traverse PLACEABLE cells — effectively making PLACEABLE cells impassable barriers. If intentional, document explicitly in the mission's GridConfig comment; otherwise keep W ≤ 20. **Design confirmation (S3-09, 2026-07-06, game-designer):** Value confirmed as-is at 10.0 — the "9 extra PATH-cell steps absorbed before a PLACEABLE shortcut becomes preferred" threshold was evaluated against the too-low (cost=2.0, placement becomes ineffective as monsters constantly cut through tower zones) and too-high (cost=50.0, shortcuts never trigger, pathfinding takes longer) failure modes described in `production/stories/core/s3-09-placeable-cost-confirmation.md`, and 10.0 was judged the correct mid-game "forcing" threshold. No code change required (`PLACEABLE_COST` in `src/foundation/pathfinding/pathfinding_system.gd` remains 10.0). Closes Sprint 2 QA sign-off advisory item 3. |
| `pathfinding_path_cost` | Pathfinding (this GDD) | 1 | 1 only | Cost per step on PATH, SPAWN, GOAL cells. Fixed at 1 — the ratio between PATH and PLACEABLE is what matters. Do not change. |
| `grid_cols` / `grid_rows` | Grid GDD | 16 × 12 | 10–24 × 8–18 | Grid dimensions determine template length and A* search space. Larger grids increase rebuild time (provisional — negligible at ≤ 400 cells per OQ-3; validate empirically before Sprint 2 gate). Typical template paths: 20–40 cells. |
| `pathfinding_fallback_warning` | Pathfinding (this GDD) | enabled | toggle | Whether `push_warning()` fires (and `last_fallback_warning` is set) when fallback A* is used (monster off-template). | `pathfinding_max_fallbacks_per_frame` | Pathfinding (this GDD) | 1 | 1–5 | Max standalone fallback A* builds per physics frame. ## Visual/Audio Requirements

The Pathfinding System has no visual or audio output. It is silent infrastructure. All player-perceivable effects of path computation are expressed through the Monster System (monsters changing direction) and the Tower System (blocked-placement UI indicator surfacing the `would_block_all_paths()` result). The Pathfinding System neither renders anything nor triggers audio events.

**Debug visualization (development builds only):** A debug overlay may render active route templates on the grid as colored line segments per SPAWN — one color per SPAWN cell. This overlay is toggled via a debug flag and never ships to players. Implementation is out of scope for MVP.

## UI Requirements

The Pathfinding System exposes no UI of its own. Its only UI-adjacent output is the boolean returned by `would_block_all_paths(footprint)`. The Tower System reads this value and is responsible for surfacing the blocked-placement indicator to the player (cursor color change, shake animation, or equivalent). Pathfinding defines the contract; the Tower System owns the presentation.

No other UI requirements exist for this system.

An implementation that passes ≤1ms on quiescent frames but spikes to 3–5ms during GC collection fails this AC. Cross-reference: Monster System AC-28 (2ms total `_physics_process()` budget — `get_path()` sub-budget must fit within that envelope). (O(1) dictionary lookup + O(k) `Array[Vector2i]` Variant copy per call — see F3 Variant overhead note.)
**GC-force mechanism:** Godot 4 has no direct `GC.collect()` API. To force a GC cycle before measurement: allocate and discard ≥10 MB of throwaway Array data immediately before the measurement window — e.g., `var _gc_trigger: Array = []; for i in 400000: _gc_trigger.append(Vector2i(i, i)); _gc_trigger.clear()`. This allocation pressure reliably triggers a collection on the next GC-eligible frame. **Measurement protocol:** Use `Time.get_ticks_usec()` before and after each `get_path()` call. Record 100 samples per physics frame over the 10-second window. Report p99.9 across all samples including GC frames.
**Pre-approved remediation fallback:** If the p99.9 GC-inclusive budget fails, the pre-approved remediation is the **index+template-reference** approach (OQ-6 option b): `get_path()` returns a `{template_ref: ref, start_index: int}` struct instead of copying the array slice. This eliminates per-call Variant allocations at the cost of changing the Monster System API contract at every `get_path()` call site. This path is pre-approved to prevent a mid-sprint Monster System API redesign decision. OQ-6 must measure both the quiescent-frame p99 and the GC-inclusive p99.9 before Sprint 2 gate.
