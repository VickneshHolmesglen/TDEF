# Quick Design Spec: Main Menu

**Type**: New Small System
**Scope**: A new top-level boot scene (`res://src/scenes/MainMenu.tscn`) shown before Sanctuary. Presents real background art and 3 real, functional buttons (PLAY, SETTINGS, QUIT). Does not touch Sanctuary UI, Mission Select, or Encyclopedia's own internal design — only adds the one new screen that precedes them.
**Date**: 2026-08-01
**Estimated Implementation**: 2-3 hours

## Overview

Main Menu is the first screen the player sees on launch — a static, non-interactive scenic background (user-provided art) with a real "Sanctuary Defenders" title/logo and a vertical stack of 3 real nav buttons. PLAY transitions into the existing SANCTUARY context via `GSceneManager.transition_to_sanctuary()` — the same real entry point Tarot Deck UI and Sanctuary UI's own Launch/Depart flow already use. SETTINGS opens a minimal placeholder screen (no real Settings system exists in this project yet — matches the project's own "mechanism real, content placeholder" convention rather than fabricating settings that don't exist). QUIT calls `get_tree().quit()`.

`project.godot`'s `run/main_scene` changes from `the_gap.tscn` to `MainMenu.tscn` — this is a real, visible change to the game's boot flow, called out explicitly since it affects how every future session/test that boots the "real" project (not a specific test scene) will start.

## Core Rules

1. `MainMenu.tscn` is a `Control` root, full-rect anchored, with:
   - A `TextureRect` background using the user-provided `assets/art/main-menu/background.png` (cropped/processed from `Main Menu Clean.png` — the version without baked-in placeholder title text).
   - A `Label`/title node reading "Sanctuary Defenders" (this project's real name — the source art's baked-in "TOWER DEFENSE / PROTECT THE KINGDOM" text is not used, per the Clean variant being provided specifically to avoid it).
   - A vertical `VBoxContainer` of 3 real buttons, cropped from the user-provided `Main Menu Buttons.png` sheet: **PLAY**, **SETTINGS**, **QUIT** — in that order, matching the sheet's own top-to-bottom ordering with UPGRADES/ENCYCLOPEDIA/ACHIEVEMENTS rows removed.
2. **PLAY** calls `GSceneManager.transition_to_sanctuary()` directly. No new SceneManager API needed — this is the exact same call Tarot Deck UI's own Cancel/return path and Sanctuary UI's re-entry already use (per `scene_manager.gd`'s existing public API).
3. **SETTINGS** opens a minimal placeholder `Control` (a full-rect panel with a "Settings — Coming Soon" label and a Back button returning to Main Menu). Real Settings content (video/audio/input options) is explicitly out of scope — no Settings GDD exists anywhere in this project.
4. **QUIT** calls `get_tree().quit()` directly. No confirmation dialog (not requested, keeps scope minimal).
5. **Dropped from the source art, not built**: UPGRADES button, ENCYCLOPEDIA button (no real screen exists — GDD's own OQ-5 leaves this undecided, not this task's call to make), ACHIEVEMENTS button, the 4 social/store icons (Discord/Twitter/Trophy-store/Mail), and the "NEWS — New Map Pack Available" panel. None correspond to a real system in this project.
6. ~~No keyboard/gamepad focus-ring wiring in this pass~~ — **Added 2026-08-01 (same day, follow-up request)**: `MainMenu.tscn` gained its own `InputModeTracker` child (matching InventoryScreen's pattern, not Mission HUD's injected-tracker variant, since this screen has no outer owner to inject one). All 4 real interactive buttons (PLAY/SETTINGS/QUIT plus the Settings placeholder's own Back button) get a `FocusRingFactory` ring, gated on `has_focus() AND InputModeTracker.is_focus_ring_visible()` — the same ADR-0011 rule InventoryScreen/Mission HUD already use. PLAY grabs initial focus on `_ready()` (no prior screen in this project does this, but a menu with nothing focused is unnavigable by gamepad/keyboard alone until the first mouse move); opening/closing the Settings placeholder moves focus to/from its Back button correspondingly.

**Fixed same day (follow-up request)**: the Settings placeholder previously didn't trap Tab-focus — pressing Tab while it was open could cycle focus back onto the underlying PLAY/SETTINGS/QUIT buttons, visually covered but not focus-excluded. Fixed by setting those 3 buttons to `Control.FOCUS_NONE` for the duration the panel is open (`_set_underlying_buttons_focusable()`), restoring `FOCUS_ALL` on close — leaving Back as the only focusable Control in the tree while the modal is up. Live-verified via Godot MCP (the exact original repro: click SETTINGS, press Tab, focus stays on Back) plus 3 new tests.

## Tuning Knobs

None — this is a static presentation screen with no gameplay-affecting values.

## Acceptance Criteria

- [x] Launching the real project (not a specific test scene) shows `MainMenu.tscn` first, not `the_gap.tscn` — live-verified via Godot MCP
- [x] PLAY transitions to the real SANCTUARY context (`scene_transition_completed(target_context="SANCTUARY")` fires, Sanctuary UI mounts at `OVERVIEW`) — live-verified via Godot MCP (screenshot + zero debug-output errors) and `test_play_button_transitions_to_sanctuary`
- [x] SETTINGS shows the placeholder screen; its Back button returns to Main Menu — live-verified + `test_settings_button_shows_the_placeholder_panel`/`test_settings_back_button_hides_the_panel_again`
- [x] QUIT exits the application — `get_tree().quit()`, standard API, not live-tested (would terminate the verification session)
- [x] No regression: existing test suites that boot `the_gap.tscn` directly (via explicit `scene` parameter, not the project default) are unaffected — full regression clean at 1837/1837 after both passes (the boot-scene change and the focus-ring addition)
- [x] Focus rings appear on the initially-focused button and follow keyboard/gamepad navigation, hide on mouse motion, and correctly move to/from the Settings placeholder's Back button — live-verified via Godot MCP (screenshots at each state) + 5 new tests

## Systems Index

This is below systems-index tracking threshold — a single static presentation screen with 3 buttons, no gameplay logic, no cross-system dependencies beyond a single existing `SceneManager` call. Quick spec is sufficient, matching this doc's own stated threshold for what needs full GDD tracking.
