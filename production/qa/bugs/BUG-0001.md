# Bug Report

## Summary
**Title**: Tarot's unlocked-card ledger is silently dropped from any save made outside TarotDeckUI
**ID**: BUG-0001
**Severity**: S1-Critical (silent, unrecoverable player-data loss)
**Priority**: P2-Next Sprint (no player-facing symptom yet — no card is currently unlockable through play at all until BUG scope below is fully wired — but must be fixed before Building Upgrade's `"tarot"`-requirement type or any other Sanctuary-reachable Tarot consumer ships)
**Status**: Closed
**Reported**: 2026-08-12
**Reporter**: Claude Sonnet (found during Building Upgrade System's `/design-review`)

## Classification
- **Category**: Gameplay / Save-Persistence
- **System**: Tarot
- **Frequency**: Always (100% of saves performed while the player is not inside `TarotDeckUI.tscn`)
- **Regression**: Unknown — architectural since Tarot's introduction (ADR-0027, scene-instanced-not-Autoload by design); not caused by a recent change

## Environment
- **Build**: main @ a9fe0a5 (2026-08-12)
- **Platform**: N/A — pure GDScript/Godot lifecycle bug, not platform-specific
- **Scene/Level**: Any scene other than `TarotDeckUI.tscn` (Sanctuary overview, any mission, any other Sanctuary room)
- **Game State**: N/A — reproduces regardless of save content

## Reproduction Steps
**Preconditions**: A save file exists or is being created.

1. Be anywhere in the game other than the Tarot Deck UI screen (`TarotDeckUI.tscn`) — e.g. Sanctuary overview, a mission, Defense Building's screen.
2. Trigger a save (`GSavePersistence.save_slot()`).
3. Inspect the resulting save payload's `"tarot"` key (or reload and inspect `Tarot`'s restored `_card_unlocked`/`_mastery_missions_played`/`_rune_discovered`/`_current_deck` state).

**Expected Result**: Tarot's full persisted state (unlocked cards, mastery, rune discovery, deck template) is present in the save and restores correctly.
**Actual Result**: Tarot's save data is entirely absent from the save payload. `Tarot._ready()` calls `GSavePersistence.register(self, RESTORE_ORDER)` and `_exit_tree()` calls `unregister()` — but `Tarot` is only ever instanced as a child of `TarotDeckUI.tscn` (`tarot.gd`'s own doc comment: "deliberately scene-instanced, not an Autoload... its one real instance lives as a shell-owned child of TarotDeckUI.tscn"). `GSavePersistence.save_slot()` iterates its `_registered_systems` array at call time — so any save taken while `TarotDeckUI.tscn` is not mounted silently omits Tarot from the save, with no error, warning, or fallback.

## Technical Context
- **Likely affected files**:
  - `src/core/tarot/tarot.gd` (`_ready()`/`_exit_tree()` register/unregister, lines ~116-130)
  - `src/foundation/save_persistence/save_persistence.gd` (`_registered_systems`, `register()`/`unregister()`, `save_slot()`)
  - `src/presentation/tarot_deck_ui/TarotDeckUI.tscn` (Tarot's only current instantiation site)
- **Related systems**: Defense Building (`is_tech_unlocked()` now feeds Tarot's own `is_card_unlocked()` per the 2026-08-12 tarot-unlock-wiring commit — unaffected by this bug, since that check is live/pull-based, not save-dependent); Building Upgrade (its `"tarot"`-requirement type already fails closed for an unrelated reason — no live Tarot instance reachable from Sanctuary UI — this save bug is a second, independent consequence of the same root architectural gap)
- **Possible root cause**: Tarot was deliberately designed as scene-instanced rather than an Autoload (ADR-0027), on the assumption its one screen's own lifecycle was a sufficient container for its state. That assumption breaks for save/persistence, which must be reachable regardless of which screen is currently mounted — the same class of gap Building Upgrade's own `/design-review` (2026-08-12) separately found for the `"tarot"`-requirement check. **The GDD's originally-proposed fix for the requirement-check gap (giving Tarot a second shell-owned instance inside `SanctuaryUI.tscn`) would not fix this bug and would make it worse** — two never-simultaneously-alive instances, neither of which persists across the boundary, with no state handoff between them (verified live by a godot-specialist review pass). The architecturally sound fix is very likely converting Tarot to a true Autoload (single persistent instance surviving every `SceneManager` transition) — but that is a real design decision needing its own ADR from Tarot's own owner, not asserted as the final answer here.

## Notes
Not caused by, and not fixed by, the 2026-08-12 "wire Tarot card unlocking to Defense Building's tech tree" commit (`a9fe0a5`) — that change made `is_card_unlocked()` a live pull-based check against `GDefenseBuilding`, which is itself an Autoload and unaffected by this bug's save-registration gap. This bug is specifically about Tarot's OWN state (`_card_unlocked`'s non-tech seam, `_mastery_missions_played`, `_rune_discovered`, `_current_deck`) failing to reach the save file at all outside `TarotDeckUI`.

## Verification Record
**Verified**: 2026-08-12
**Method**: Live Godot MCP probe against the real spawned project (no `TarotDeckUI.tscn` mounted anywhere) confirmed `GSavePersistence._registered_systems` contains a `key == "tarot"` entry — the exact condition that previously resolved `false`. Full detail: `production/qa/evidence/tarot-autoload-conversion-evidence.md`.
**Regression test**: `tests/integration/tarot/autoload-persistence-reachability_test.gd` (2 tests, passing) — inverts this bug's own reproduction case into a permanent regression check.
**Fix**: ADR-0035 (Tarot Autoload Conversion) — Tarot converted from a `TarotDeckUI.tscn`-child scene-instanced node to a true Autoload (`GTarot`). No change was needed to Tarot's own `register()`/`unregister()` calls — they already matched every other Autoload `SaveRestorer`'s convention; only *where* they fired was wrong.
**Verdict**: VERIFIED FIXED
